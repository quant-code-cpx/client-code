# AI 研究工作台模型韧性修复 Round 8（2026-08-07）

## 结论

Round 7 暴露的 3 个“结构化输出校验失败”与自动路由长尾均为可修复的后端问题，已完成代码修复、自动化回归与服务重建。它们并非模型的 384,000 输出能力不足。

## 根因

模型部署的 `max_output_tokens` 为 384,000，但工作流将 `AGENT_MAX_INPUT_TOKENS=32,768` 错当作输出预留的基数，再乘 `AGENT_CONTEXT_OUTPUT_RESERVE_RATIO=15%`，最终对实际 `SYNTHESIZE` 请求下发仅 `4,915` tokens。

同时，flash 默认使用 `HIGH` 推理档。Round 7 审计中，合成阶段平均推理 token 为约 1,631，最高约 3,661；高推理消耗叠加 4,915 的小输出上限，导致严格 JSON 在 `length` 或 `stop` 后仍失败。原链路只做一次 JSON repair，随后即使备用 pro 可用也禁止切换，最终使整轮 Agent 失败。

## 修复

1. 输出额度以模型**安全上下文窗口**计算，不再由 Run 的输入上限计算。当前 1,000,000 上下文、384,000 模型上限、8% 安全边界和 15% 预留比得到 `138,000` tokens；仍受模型上限和安全窗口约束。
2. 最终合成与引用修复在目标模型声明支持 `LOW` 时使用低推理档；规划阶段保留模型默认档位。
3. 同一模型的 JSON repair 已耗尽仍非法时，将其标记为可恢复的 `INVALID_OUTPUT`，安全切到备用模型。下一模型会重置结构化预览，已验证的内容才会持久化，不会将半截 JSON 作为最终回答。
