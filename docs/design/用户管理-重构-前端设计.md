## 一、功能要点提炼与补充（PM 视角）

### 1.1 用户原始诉求复述

> 用户原话："重新审视用户管理页面，看看是否有要优化的点，落实到文档，需要后端支持的点也落到文档。"

即：以现状盘点为出发点，找出页面上可优化的 UE / 信息架构 / 数据 / 安全 / 合规问题，并把需要后端配合的项目独立列出，便于排期对接。

### 1.2 模块定位与价值主张

- **30 秒内回答**：当前系统里有谁、谁是管理员、谁被禁用、谁刚被新建、谁动了什么。
- **3 分钟内完成**：新建账号/调整配额/禁用账号/重置密码/查询某次操作的责任人和上下文。
- **边界声明**：
  - 「个人自助修改资料/改密」属 `/profile`，不在本页。
  - 「登录认证、Token 刷新」属 `/auth`，不在本页（但其安全事件应进入审计日志，见 1.4）。
  - 「角色权限矩阵的可视化与编辑」属未来「权限策略」模块，本次不扩展，仅明确角色可调整即可。

### 1.4 资深从业者补充（行业最佳实践）

> 站在管理员日常运维 + 风控合规视角，补充用户没说但必备的：

1. **账号锁定与解锁** — 风控基线。当前后端无锁定字段，前端也无解锁动作。一旦遭遇暴力破解，管理员只能通过"重置密码"绕过，**留下的审计语义错误**（reset 而非 unlock）。
2. **角色调整审计** — 现 update API 禁改 role；只能"删除重建"，但删除会带走该用户所有自选股/策略/回测，业务影响极大。**实际上 ADMIN ↔ USER 升降权是高频且高敏感动作，必须独立接口、独立审计 action（`USER_UPDATE_ROLE`）**。
3. **邀请流程替代代设密码（本期不做）** — 管理员手动设的初始密码靠口头/IM 传给当事人，存在二次泄漏风险。行业实践是发送一次性邀请链接（含 token，24h 失效，首次登录强制改密）；但本期确认暂不纳入，前端不展示邀请入口、不接入邮件服务，作为后续 Backlog 记录。
4. **登录类安全事件入审计** — 现审计仅五个 `USER_*` 操作，缺登录侧。"昨晚 3 点谁登的、是不是异地、有没有失败爆破"是安全运维的第一问。
5. **字段级 diff** — 现状 `details` 字段是 `Record<string, unknown>`，前端用 `<pre>` 直接 JSON.stringify。审计场景必须能一眼看见"昵称：张三 → 李四"这种结构。需后端约定 schema：`{ before: {...}, after: {...} }` 或 `{ changes: [{ field, before, after }] }`。
6. **配额含义可视化** — `-1 = 不限`是工程语义，UI 必须用"不限 / 具体数字"切换控件，避免人工填错为 0（=完全禁用回测）。
7. **已删除（DELETED）用户的去向** — 软删除但前端筛选下拉只有「正常 / 已禁用」，无法看到/恢复 DELETED 用户。该状态等同"消失"，后端软删除的价值被前端废掉。需提供"包含已删除"开关 + 恢复动作。
8. **导出与合规** — 金融行业内控/外审常需"近 12 个月所有人事变动"。审计日志和用户列表都需要 CSV 导出（中文表头、UTF-8 BOM）。
9. **页面状态可分享** — 复盘事故时常需"把这个筛选好的链接发给同事"，URL 必须承载所有筛选/分页状态。
10. **会话与多设备** — 后端如已有 token 体系，应能展示某用户的活跃 session 列表 + 强制下线按钮（本次设为 P2，单列一节占位）。

### 1.5 已确认决策（2026-05-02）

- [x] **Q1**：邀请链接流程**不纳入本期**；本期不规划邮件服务、不接入 `/api/user/invite`，仅保留手动创建账号 + 初始密码回显能力。
- [x] **Q2**：登录类安全事件采用推荐方案：**并入用户审计 action**，不新增 `/api/security/event/list`；后端扩展审计 action 与 `details/result` schema，前端在审计日志 Tab 统一展示。
- [x] **Q3**：批量操作采用推荐方案：**允许部分成功**，返回成功 ID 与失败明细；前端展示进度与成败明细表，避免一条失败导致整批回滚。
- [x] **Q4**：删除用户采用推荐方案：**用户软删除，名下业务数据不级联删除**；自选股、策略、回测、订阅保留归档关系，删除确认弹窗展示影响清单，恢复用户后恢复可见性。
- [x] **Q5**：**不允许** `SUPER_ADMIN` 编辑/降权另一名 `SUPER_ADMIN`；维持 `canManage('SUPER_ADMIN') === false`，仅保留只读展示与 Tooltip 解释。

### 5.2 关键技术点

- **URL 状态管理**：复用项目内已有的 `useSearchParams` + `pickDefined` 模式（参考自选股重构）。
- **Autocomplete 防抖**：`useDeferredValue`（React 19）或自写 200ms debounce，AbortController 取消旧 search。
- **批量操作并发**：使用 `Promise.allSettled`，限流 5 并发；进度按已结算条数计算。
- **随机密码生成**：`crypto.getRandomValues(new Uint8Array(16))` → base64url，剔除歧义字符 `0OIl1`。
- **CSV 导出**：前端拼装 BOM `\uFEFF` + CRLF；若数据量大（> 1k 行）走后端导出接口，前端只触发下载。
- **可访问性**：表头排序加 `aria-sort`；Checkbox 加 `aria-label="选择 {account}"`；批量条加 `role="region" aria-live="polite"`。
- **类型对齐**：`UserListQuery.sortBy` 与 `UserManageItem` 字段保持同源，建议导出 `UserSortableField` 联合类型并在两处复用。

- **审计 details 兼容**：`changes` 缺失时回退到现 JSON pre。

### 7.2 字段扩展

| 数据契约           | 新增/调整字段                                                                                                                                                                                | 说明                                              |
| ------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------- |
| `UserManageItem`   | `lastLoginAt?: string \| null`<br>`updatedAt?: string \| null`<br>`lockedUntil?: string \| null`<br>`loginFailCount?: number`                                                                | 列表展示与状态判定                                |
| `UserListQuery`    | `includeDeleted?: boolean`<br>`createdFrom?: string`<br>`createdTo?: string`<br>`lastLoginFrom?: string`<br>`lastLoginTo?: string`                                                           | 时间区间与软删除筛选                              |
| `AuditAction`      | 增加 `LOGIN_SUCCESS`、`LOGIN_FAILED`、`LOGOUT`、`TOKEN_REFRESH`、`USER_UNLOCK`、`USER_UPDATE_ROLE`、`USER_RESTORE`、`USER_BULK_UPDATE_STATUS`、`USER_BULK_UPDATE_QUOTA`                      | 安全事件 + 新动作进入审计；`USER_INVITE` 本期不做 |
| `AuditLogItem`     | `result?: 'success' \| 'failure' \| 'blocked'`<br>`details.changes?: Array<{ field: string; before: unknown; after: unknown }>`<br>`details.reason?: string`<br>`userAgent?: string \| null` | 结果分级 / 字段级 diff / 客户端环境               |
| `AuditLogQuery`    | `result?: 'success' \| 'failure' \| 'blocked'`<br>`actions?: AuditAction[]`（多选）<br>`operatorAccount?: string`<br>`targetAccount?: string`                                                | 多操作类型筛选与按账号筛选                        |
| `ResetPasswordDto` | `notifyEmail?: boolean`                                                                                                                                                                      | 系统直发到用户邮箱（避免管理员人工传递）          |
| `CreateUserDto`    | 兼容现有；`password` 本期仍为必填                                                                                                                                                            | 邀请分支不纳入本期，不要求 `/create` 支持无密码   |

### 7.3 审计行为约束

- 所有以下动作必须自动写入审计日志：登录成功 / 失败 / 登出 / Token 刷新失败、解锁、调整角色、恢复、批量操作（每条独立写入或聚合写入由后端定）。
- 失败动作（如非法权限、参数错误、唯一约束冲突）也应写入，`result='failure'`，`details.reason=后端错误码或文案`。
- 字段变更类（USER_UPDATE_INFO、USER_UPDATE_ROLE、USER_UPDATE_STATUS、配额变更）必须在 `details.changes` 中产出 `field/before/after` 三元组。

### 7.4 安全相关

- 锁定阈值与时长由后端配置（建议：连续 5 次失败锁 30 分钟），前端只展示 `lockedUntil`。
- 邀请链接本期不做；若后续启动，token 必须一次性 + 24h 失效，且首次登录强制改密。
- 导出接口必须做权限校验 + 速率限制（避免被作为数据泄露通道）。
