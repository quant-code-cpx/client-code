## 一、功能要点提炼与补充（PM 视角）

### 1.1 用户原始诉求复述

> "重新审视事件日历页面，看看是否有要优化的点，落实到文档，需要后端支持的点也落到文档。"

用户未指定具体功能项，要求**全面体检 + 优化建议**，并显式要求"后端支持点必须列出"。本设计据此对现状做穷尽盘点，再以三视角提出优化方向。

### 1.2 模块定位与价值主张

- **30 秒回答**：未来一段时间，我关心的股票/全市场会发生哪些可能扰动股价的事件？
- **3 分钟动作**：按事件类型/时间窗筛选 → 快速识别"今天/明天/本周"重点事件 → 跳转到个股或新建研究笔记 → 订阅持续提醒。
- **边界声明**：
  - 与 **预警与监控（价格/异动/涨跌停）** 区隔：本模块只承担"已知日程型事件"（披露/解禁/分红/预告/IPO/可转债/股东增减持），价格类预警留在 `alert-price-rules` / `alert-anomalies`。
  - 与 **事件驱动研究（event-study）** 区隔：本模块是**日程视图 + 提醒**，不做 AAR/CAAR 统计建模；点击单事件可跳转到 event-study 做后续分析。
  - 与 **首页 Today Brief** 区隔：本模块是详尽视图，首页只展示"今日 + 未来 3 日 Top N"摘要卡。

### 1.4 资深从业者补充（行业最佳实践）

> 站在二级市场实战视角，列用户没说但**做交易必备**的项，并说明"为什么补充"。

| 补充项                                      | 为什么补充                                                                                            |
| ------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| **事件影响力评分（impactScore）**           | 一天可能 200+ 财报披露，没有排序等于没有信息。Bloomberg / Wind 标配 1-5 星或权重值。                  |
| **历史同类事件走势对比**                    | "上次解禁 800 万股次日跌 4%"——量化决策必须看历史样本。对接 event-study 的事后窗口收益。               |
| **解禁市值占流通市值比 / 业绩预告变动幅度** | 同样是解禁事件，1% vs 30% 流通占比天差地别；业绩预告 +200% vs +5% 也是。**字段是事件本质**。          |
| **预约披露 vs 强制披露 状态**               | 财报披露前夕的"提前披露 / 推迟披露"是异动信号源，必须暴露。                                           |
| **股东增减持类型细分**                      | 减持人是控股股东 vs 高管 vs 大宗交易，市场反应完全不同。需要 `subType` + `holderType` + `changePct`。 |
| **可转债条款关键节点**                      | 转股价下修 / 强赎 / 回售触发——正股必爆量，但当前事件类型未细分这些节点。                              |
| **板块/概念归属**                           | 分析师按板块看事件聚集（如"半导体本周 12 家披露"）。需后端在事件上挂板块标签。                        |
| **跨市场标记**                              | A/H 股、AB 股、ADR——同一公司在不同市场披露时间不同，应有 `market` 标记防止重复阅读。                  |
| **节假日/停牌冲突标识**                     | 周五披露 + 周一停牌，对持有者意义重大。日历应叠加交易日历高亮。                                       |
| **"复盘视角"切换**                          | 实战中除了看未来事件，**复盘"上周哪些事件落地后涨/跌最多"**也是高频动作。提供"过去模式"+收益条。      |

### 1.5 决策清单（已定稿，2026-05-01）

- [x] **Q1 → 实现，依赖后端**：事件订阅本期实现；推送通道 MVP 仅 "站内消息"；邮件/微信留作 v3。**后端能力清单见第八章"后端提示词"**。
- [x] **Q2 → 后端给评分**：影响力评分由后端按规则/模型给出 `impactScore (0-100)` 与 `impactLevel ('HIGH'|'MEDIUM'|'LOW')`；前端不再做规则估算，缺字段时前端按 §7.4.2 降级。

- [x] **Q5 → 同意**：默认日期窗口改为 `[今日, 今日+14日]`，提供 "未来 / 历史" 切换 Tab。

### 2.2 不足之处（按严重性排序）

| #   | 问题                                                                                                                               | 影响                                                                 | 触发场景                |
| --- | ---------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------- | ----------------------- |
| 1   | **只有时间线一种视图**                                                                                                             | 30 天范围扫盘极慢；无法形成"密度直觉"                                | 任何超过 1 周的查询     |
| 2   | **`fetchEvents` 无 `AbortController`**（[view.tsx#L30-L46](src/sections/alert/view/alert-calendar-view.tsx)）                      | 快速切换日期/类型时存在响应乱序 race；旧响应可能覆盖新数据           | 用户连续点选筛选条      |
| 3   | **`EVENT_TYPE_CONFIG` 重复定义**（[timeline.tsx#L23-L30](src/sections/alert/alert-calendar-timeline.tsx) vs stats.tsx）            | 改一处忘改另一处 → 颜色/标签不一致                                   | 维护时                  |
| 4   | **无影响力评分 / 排序维度**                                                                                                        | 同一天的事件按"日期"扁平展示，30 个事件无主次                        | 周一/周五披露日         |
| 5   | **无"我的自选股"维度**                                                                                                             | 全市场事件淹没用户真正关心的几支股                                   | 默认场景                |
| 6   | **`detail` 字段是单字符串**（[alert.ts#L17-L23](src/api/alert.ts)）                                                                | 信息密度低，无法显示金额/比例/对比；列表与"详情"无区分               | 任何事件                |
| 7   | **无单事件详情视图**                                                                                                               | 用户必须跳到股票详情页拼凑信息；研究链条断裂                         | 想了解任一事件          |
| 8   | **无导出/订阅**                                                                                                                    | 事件日历无法沉淀到本地工作流（Outlook/Apple Calendar）；离线后漏事件 | 离线 / 跨设备           |
| 9   | **URL 不持久化筛选**                                                                                                               | 刷新页面回到默认；分享链接传不出筛选条件                             | 链接分享、F5            |
| 10  | **筛选缺板块/市值/自选股/影响力四个维度**                                                                                          | 业内通用维度全缺                                                     | 任何专业用户            |
| 11  | **无空态 vs 加载中区分细节**：空态文案居中提示但缺"调整建议链接"                                                                   | 用户面对零结果无 next-step                                           | 极窄筛选时              |
| 12  | **`tsCode` 跳转用 query string `/stock/detail?code=`**（[timeline.tsx#L145-L150](src/sections/alert/alert-calendar-timeline.tsx)） | 与项目其它跳转方式不一致；难做"新标签打开"hover 预览                 | 列表行点击              |
| 13  | **字号 0.875rem ≈ 14px** 没问题但**详情字段拥挤**：标题 + 摘要 + 代码挤一行                                                        | 阅读疲劳；移动端断行                                                 | 标题较长事件            |
| 14  | **无与 `apiFetchDate` 共享日期上下文**                                                                                             | 跨模块切换日期需要重设                                               | 与行业/资金动态串联使用 |
| 15  | **统计卡只有"计数"**                                                                                                               | 无"今日 / 明日 / 本周 / 已过期"分桶；无 Top 影响力概览               | 想知道近期热度          |
| 16  | **无键盘可达性**：日期切换、类型勾选无 hotkey                                                                                      | 高频用户体验差                                                       | 重度用户                |
| 17  | **无错误重试按钮**：Alert 错误后用户只能改筛选触发刷新                                                                             | 网络抖动后体验差                                                     | 偶发 5xx                |
| 18  | **`getCalendar` 默认 30 天**：用户语义其实想要"前瞻视角"                                                                           | 事件日历的本质是"未来"——当前默认是"回看"                             | 首次进入                |

## 三、功能细化拆分

### 3.1 模块结构树


### 3.2 子模块逐个细化

#### 3.2.1 HeaderBar

- **职责**：标题 + 视图切换（ToggleButtonGroup：月历 / 时间线 / 表格）+ 操作按钮（刷新 / 导出 / 订阅 / 帮助 Tooltip）
- **数据**：无
- **交互**：视图切换不重置筛选；导出/订阅触发对应 Drawer/Dialog
- **状态**：无

#### 3.2.2 FiltersBar

- **职责**：所有筛选输入；筛选改变时通过 URL 同步并触发查询
- **数据**：消费 `useFetchDateContext`、`useWatchlist`、`useSectorOptions`
- **交互**：
  - 日期：`DateRangePicker` + 快捷段（今日 / 本周 / 未来 14 日 / 上周）
  - 范围：`ToggleButtonGroup` 全市场 / 自选股 / 组合持仓
  - 类型：Chip 多选 + 全选/反选
  - 板块：`Autocomplete`（多选，含搜索）
  - 市值：分档（< 50 亿 / 50-300 / 300-1000 / > 1000）
  - 影响力：高/中/低三档复选
  - 文本搜索：模糊匹配 `tsCode | stockName | title`
- **状态**：所有值通过 `useSearchParams` 持久化
- **边界**：分桶值与后端枚举一致；为零结果时给"清除筛选"按钮

#### 3.2.3 StatsRow

- **职责**：4 张"动作卡"
- **卡片定义**：
  | 卡片 | 主指标 | 副指标 | 点击动作 |
  | --------------- | ----------------------------- | ---------------------------- | --------------------------- |
  | 今日事件 | 今日总数 | 高影响力数 | 跳到日期 = 今日 |
  | 本周新增 | 未来 7 日事件总数 | 自选股相关数 | 跳到日期 = 本周 |
  | Top 影响力 | 影响力 Top 1 事件标题 | 距事件天数 | 打开该事件 Detail Drawer |
  | 自选股相关 | 自选股相关事件总数 | 最近 1 个事件距当前天数 | 范围切到"自选股" |
- **状态**：loading 用 Skeleton；空态显示 0 + 灰色

#### 3.2.4 CalendarGridView（月视图）

- **职责**：标准月历网格，每天单元格显示该日事件密度色阶 + 事件 chip 缩略
- **数据**：前端按 `date` 聚合
- **交互**：
  - 单元格 hover → 弹出 Popover 列出当天前 10 条事件
  - 单元格点击 → 当日事件 Drawer（与 Detail Drawer 共用）
  - 事件 chip 直接点击 → 该事件 Detail Drawer
  - 月份切换：← / → 按钮 + "回到今日"
- **状态**：单元格分 `今日 / 工作日 / 周末 / 节假日 / 已过期` 5 态
- **边界**：单日事件超过 5 条折叠为 "+N"；超过 30 天范围禁止月视图（提示切到时间线）

#### 3.2.5 TimelineListView（重构）

- **职责**：按日期分组的卡片列表（保留现有结构，升级行内信息）
- **行布局**：

- **状态**：每个日期分组卡可折叠；空态、loading 与现有一致

#### 3.2.6 TableView（新增）

- **职责**：高密度表格视图，支持多选导出
- **列**：日期 / 类型 / 代码 / 名称 / 板块 / 标题 / 影响力 / 关键数值 / 操作
- **交互**：列排序；多选 + 顶部导出 CSV/ICS；密集行高 36px
- **状态**：使用 MUI `DataGrid` 或自封表格组件（与项目其他表格风格一致）

#### 3.2.7 EventDetailDrawer

- **职责**：单事件深度信息
- **数据**：调用 `alertApi.getCalendarDetail(eventId)`（**新接口**）
- **结构**：

  - Block 5：操作区（订阅同类 / 加自选 / 新建笔记 / 复制详情）

### 3.3 数据流与状态管理

```
URL Query
  ↓ useSearchParams
FiltersState (Context, 模块内)
  ↓ debounce 200ms
fetchEvents(AbortController)
  ↓
events: CalendarEvent[]  ─→ StatsRow（前端聚合）
                         ─→ CalendarGridView（按日期 group）
                         ─→ TimelineListView
                         ─→ TableView

事件点击 → eventId → EventDetailDrawer.open(eventId)
                  ↓
                  fetchCalendarDetail(eventId)
                  ↓
                  CalendarEventDetail
```

跨模块联动：

- 进入页面时 `apiFetchDate`（项目共享）作为日期默认值候选；用户改动后写回。
- 自选股范围切换时，调用 `watchlistApi.list` 获取 tsCode 集合传给 `getCalendar`（或后端支持 `scope: 'watchlist'`，详见后端清单）。

### 3.4 导出与订阅

#### 导出

- 入口：HeaderBar `导出` 按钮（带下拉：CSV / ICS）
- 行为：调用后端 `/api/alert/calendar/export`，返回签名链接或文件流；前端触发下载
- 内容：当前筛选条件下全部命中事件
- ICS 字段映射：`SUMMARY = 类型 + 标题`、`DTSTART = date`、`DESCRIPTION = detail + 关键数值`、`UID = eventId`

#### 订阅

- 入口：HeaderBar `订阅` 按钮 / Detail Drawer 的"订阅同类"
- 行为：打开 `SubscribeDialog`，编辑订阅规则
- 字段：`name` `eventTypes` `scope (全市场/自选股/特定板块/特定股票)` `triggerWindow (T-3/T-1/T+0)` `notifyChannel (站内/邮件)`
- 后端：`/api/alert/subscribe`（详见第 5 章）

6. **测试**（`__tests__/`）：详见 5.5

### 5.2 关键技术点

- **状态共享**：模块内自封 `useCalendarState` Hook（基于 `useSearchParams`），不引入全局 store
- **AbortController**：`use-calendar-events.ts` 中每次 fetch 前 abort 上一次
- **debounce**：搜索框 250ms；其他筛选立即触发
- **大列表性能**：表格视图超过 200 行启用 `react-window` 虚拟化；月视图固定 42 单元格无需虚拟化
- **memo 边界**：`CalendarCell` 按 `(date, eventCount, density, isToday)` shallow compare；避免月切换全量重渲染
- **容错**：详情接口失败 → fallback 为列表行已有字段 + "字段不全"提示
- **跨日数据**：以 `apiFetchDate` Context 决定"今日"基准，避免本机时区误判
- **导出 ICS**：后端返回 `application/octet-stream`；前端用 `URL.createObjectURL` 触发下载，文件名 `events_YYYYMMDD_YYYYMMDD.ics`

### 5.3 风险与回退

- **后端字段未到位**：影响力评分、板块、关键数值、详情接口、导出/订阅——**全部置可选**，前端在缺字段时优雅降级（隐藏对应 UI 元素而非报错）。详见 5.4。
- **路由变化（Q3）**：改路由时旧 `/alert` 用 `Navigate` 重定向到新路径，避免外链失效。
- **灰度策略**：以 `feature flag`（`config-global.ts` 中 `FEATURE_CALENDAR_V2`）控制新视图启用；可一键回退旧时间线。

### 7.1 重大缺口（架构 / 协议层）

#### 7.1.1 订阅系统应复用现有 `alert_rule` 模型，而非另起炉灶

v2 5.4.3 新增了 `/api/alert/subscribe/*` 5 个端点，但 [src/api/alert.ts](src/api/alert.ts) 中已存在的 `PriceAlertRule` 已具备完整的订阅基础设施：

- 字段：`tsCode | watchlistId | portfolioId | status | triggerCount | lastTriggeredAt`
- 状态：`ACTIVE | PAUSED | DELETED`
- 关联：单股 / 自选股组 / 组合三种 scope

**结论**：事件订阅应作为 `alert_rule` 的扩展，而非新表/新端点。具体：

| 项                   | 复用方案                                                                                                                              |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| 表                   | 沿用 `alert_rule`                                                                                                                     |
| `ruleType` 枚举扩展  | 新增 `EVENT_DISCLOSURE / EVENT_FLOAT / EVENT_DIVIDEND / EVENT_FORECAST / EVENT_IPO / EVENT_CONVERTIBLE / EVENT_SHAREHOLDER / EVENT_*` |
| `threshold` 字段复用 | 表示 `triggerWindow` 天数（如 3 表示 T-3 触发），`null` 表示 T-0                                                                      |
| `memo` 字段复用      | 存储 JSON：`{ subTypes?, sectorCodes?, impactLevels?, channels: ['INSITE','EMAIL'] }`                                                 |
| 端点                 | 沿用 `priceRule.list / create / update / delete`，不新增端点                                                                          |
| 前端                 | `subscribe-dialog.tsx` 内部调用现有 `priceRuleApi.create`，UI 上仍呈现为"事件订阅"                                                    |
| 触发规则评估器       | 后端在事件入库阶段扫描 `alert_rule where ruleType LIKE 'EVENT_%'`，匹配后写入 `notifyQueue`                                           |

**修订**：v2 §5.4.3 中 `/api/alert/subscribe/*` 5 个端点全部删除；改为后端扩展 `ruleType` 枚举 + 前端复用 `priceRuleApi`。

#### 7.1.2 数据量与分页协议必须前置约定

v2 §5.4.2 提了 `pageSize / pageNo` 但未规定上限。30 天 × 全市场 ≈ 5000~20000 条，月切换流量不可控。**新增协议**：

| 约束项                  | 取值                                                                              |
| ----------------------- | --------------------------------------------------------------------------------- |
| 单次查询最大窗口        | `maxWindowDays = 92`（季度跨度）                                                  |
| 服务端单次最大返回条数  | `maxItems = 1000`                                                                 |
| 超限响应                | 仍返回前 1000 条，且 `truncated: true`、`nextCursor` 字段；前端展示"结果已截断"条 |
| 月视图请求建议          | 强制按"月"切片（`startDate=月首, endDate=月末`），单月内分页                      |
| `CalendarResponse` 扩展 | 增加 `truncated: boolean` 与 `dataAsOf: string`（数据快照时间）                   |

#### 7.1.3 "今日"基准与 trade_calendar 集成

v2 §1.4 / §5.4.4 提了 `tradingDayConflict`，但未明确：

- **是否复用项目已有的 `trade_calendar` 接口** ：建议复用，不在事件接口内嵌节假日完整数据，仅在事件上挂 `tradingDayConflict: 'HOLIDAY'|'SUSPENDED'|null`
- **服务器当前交易日**：响应中新增 `currentTradeDate: string` 字段，**前端"今日 / T-3 / 距今天数"全部基于此字段计算**，不再用 `dayjs().format('YYYYMMDD')`，避免客户端跨夜误判

#### 7.1.4 `EventType` 与 `AnomalyType` 的长期统一抽象

`异动监控` `涨跌停明细` `事件日历` 三模块各有独立类型枚举，未来必然出现"统一事件流"诉求（订阅一处，覆盖全部触发源）。**本期不做合并**，但需在后端表设计上预留：

### 8.4 订阅系统：复用 `alert_rule`（**不新增端点**）

#### 8.4.1 `alert_rule.ruleType` 枚举扩展

在原有 `PRICE_*` 系列基础上**新增**：

```
EVENT_DISCLOSURE
EVENT_FLOAT
EVENT_DIVIDEND
EVENT_FORECAST
EVENT_IPO
EVENT_CONVERTIBLE
EVENT_SHAREHOLDER
EVENT_ANY                    -- 任意事件类型（订阅"全部事件"）
```

#### 8.4.2 字段语义复用

| `alert_rule` 字段 | 事件订阅语义                                                                                                  |
| ----------------- | ------------------------------------------------------------------------------------------------------------- |
| `ruleType`        | 上述 `EVENT_*` 之一                                                                                           |
| `tsCode`          | 单股订阅（与 `watchlistId/portfolioId` 三选一）                                                               |
| `watchlistId`     | 自选股范围                                                                                                    |
| `portfolioId`     | 组合范围                                                                                                      |
| `threshold`       | `triggerWindow` 天数（如 `3` 表示 T-3 提前提醒；`0` 表示当日）                                                |
| `memo`            | JSON 字符串：`{ subTypes?: string[], sectorCodes?: string[], impactLevels?: string[], channels: ['INSITE'] }` |
| `status`          | `ACTIVE / PAUSED / DELETED`（沿用）                                                                           |

#### 8.4.3 触发评估器

事件入库 / 影响力评分更新时，扫描 `alert_rule WHERE ruleType LIKE 'EVENT_%' AND status = 'ACTIVE'`：

1. 按 `ruleType` 匹配事件 `type`（`EVENT_ANY` 全匹配）
2. 按 `tsCode / watchlistId / portfolioId` 缩小到该规则的关注股票集合
3. 按 `memo` 中 `subTypes / sectorCodes / impactLevels` 进一步过滤
4. 按 `threshold` 计算应触发日 = `eventDate - threshold天`
5. 命中后写入 `notify_queue`，由现有通知服务派发到 `channels`

> MVP 期 `channels` 仅支持 `INSITE`（站内消息）；`EMAIL` / `WECHAT` 留作 v3 通道接入。

### 8.5 评分服务（`impact_score`）建议规则

> 后端可先用规则版，模型版后续替换。规则版打分思路（0-100）：

| 维度         | 权重 | 计算示例                                                           |
| ------------ | ---- | ------------------------------------------------------------------ | ------------ | ------ |
| 事件类型基底 | 30   | DISCLOSURE=20, FLOAT=25, DIVIDEND=15, FORECAST=25, SHAREHOLDER=20… |
| 量级修正     | 40   | FLOAT 按 `floatRatio` 线性 0~40；FORECAST 按 `                     | changePctMid | ` 分段 |
| 市值缩放     | 15   | 大盘股（>1000 亿）×0.6；小市值（<50 亿）×1.2，封顶 100             |
| 关注度       | 15   | 自选股命中数 / 板块热度（可选，缺则 0）                            |

**`impact_level` 阈值**：≥70=HIGH，40-69=MEDIUM，<40=LOW。

### 8.6 验收脚本（建议）

后端自测时按以下场景：

1. `list` 返回 30 天 + 7 类事件 + 全量新字段，`yarn build` 后前端无 TS 报错（前端 schema 校验通过）。
2. `list` 请求超过 92 天 → 返回 400。
3. `list` 命中 1500 条 → `events.length=1000`、`truncated=true`、`nextCursor` 有值。
4. 创建一条 `ruleType=EVENT_FORECAST, tsCode=600519.SH, threshold=3` 规则，灌入一条 `eventDate=今日+3` 的预告事件，验证 `notify_queue` 当日新增一条。
5. `detail` 返回 `metrics` 完整且 `relatedEvents` 排序正确。
6. `history-trend` 返回 5 个样本 + 均值序列；超出 lookback 上限报错。
7. `export?format=ics` 返回的文件可被 Apple Calendar / Outlook 正常导入。

### 8.7 与前端字段约定速查（一一对应 §5.4.1）
