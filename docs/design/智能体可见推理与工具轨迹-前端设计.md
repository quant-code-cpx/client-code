# 智能体可见推理与工具轨迹前端设计

## 1. 本轮实现边界

Agent 消息内收敛为一个 `ThinkingPanel`，按 Run 事件真实顺序展示：

- 供应商实际返回的 `model.reasoning.delta`；
- `agent.started/planning/progress`、上下文整理与完整模型调用生命周期；
- `tool.started/tool.completed/tool.failed` 以及分页读取的完整 ToolCall 摘要。

“完整思考”在产品中只能表示供应商返回给应用的全部可见文本，不表示模型私有隐藏思维链。前端不伪造供应商未返回的内容，也不用活动计数、Tool 或最终回答反推。

## 2. 契约

### 2.1 可见推理事件

```ts
type AgentReasoningDeltaEvent = {
  schemaVersion: '1.0'
  eventId: string
  sequence: number
  type: 'model.reasoning.delta'
  runId: string
  conversationId: string
  messageId?: string
  occurredAt: string
  traceId: string
  payload: {
    modelCallId: string
    attempt: number
    kind: 'FULL' | 'SUMMARY'
    delta: string
  }
}
```

- `FULL` 显示为“思考”，`SUMMARY` 显示为“思考摘要”。
- 只追加已通过运行时 Schema 校验的 `delta`；不改写、不合并成最终答案。
- 没有该事件时显示“本次运行未收到可展示推理”。

### 2.2 历史事件

```text
POST /api/agent/runs/events/list
{ runId, afterSequence, limit, eventTypes }
-> { items, nextAfterSequence }
```

`eventTypes` 只请求规划、进度、上下文整理、模型、推理和 Tool 生命周期事件，避免把最终正文分片重复拉入轨迹。面板首次展开时从 `afterSequence=0` 开始，每页 100 条，逐页显示并自动翻页到 `nextAfterSequence=null`；折叠后保留已完成缓存。响应不含 `latestEventSequence` 或 `runStatus`；权威状态仍来自 `runs/status`。每个 `items` 先经 `parseAgentSseEvent` 验证，再与实时 `thinkingEvents` 合并。

### 2.3 ToolCall 摘要

`runs/tool-calls/list` 同样按 `nextCursor` 自动翻页到末页。事件时间线保留发生顺序，ToolCall 摘要补充持久状态、耗时、输入/输出脱敏摘要、数据时点、截断和引用。两者以 `toolCallId` 聚合，不展示原始 payload、SQL 或凭据。

## 3. 交互与状态

| Run 状态 | 面板行为 |
| --- | --- |
| RUNNING | 默认展开；实时追加 reasoning、规划、模型和 Tool 事件 |
| COMPLETED | 默认折叠，但保留回看；最终答案独立显示 |
| FAILED / CANCELLED | 保留已收到轨迹与失败/取消边界，不伪装完成 |
| 刷新后 | 展开时懒加载历史，合并当前实时事件 |
| 历史失败 | 保留已加载内容，显示部分/加载失败状态 |

时间线以 `eventId` 去重、`sequence` 升序。事件和 Tool 可交错，不按文案或完成时间重排。事件与 ToolCall 都持续自动翻页到服务端返回空游标，不设置 10,000/1,000 条本地硬截断。只有请求失败、无效游标或循环游标使分页未到末页时才标记 `partial`，并保留已经加载的全部内容。

事件分页对每个新批次独立校验和排序；正常单调序列通过 `Map` 去重后直接追加，只有异常乱序批次才做线性有序合并，避免每到一页都对全部历史重新排序。ToolCall 使用 `toolCallId` Map 与稳定 ID 顺序增量合并，同一记录的新持久状态覆盖旧状态。

实时流使用两个水位：`latestEventSequence` 表示客户端真正应用到 UI 的事件，`latestPersistedEventSequence` 表示状态接口看到的服务端最新水位。状态刷新不得把前者跳到后者；断线继续时始终从前者和 `lastEventId` 补播，避免遗漏断线窗口内的推理或 Tool 事件。

## 4. 纠偏语义

当前没有“向运行中 ModelCall 注入新 Prompt”端点。用户发现方向偏差时：

1. 点击现有“停止”，等待服务端 `agent.cancelled` 或权威 Run 状态确认。
2. Composer 保留用户输入的纠偏文本。
3. 发送纠偏消息并创建新 Run，旧 Run 轨迹不变。

这保证取消和新指令都可审计，不会追溯改写已发生的模型/Tool 事件。

## 5. 安全、可访问性与性能

- reasoning 是不可信纯文本；不使用 raw HTML，不执行链接、图片、脚本或 Markdown 活动内容。
- 轨迹只在内存中投影，不写入 Composer 草稿、正式 assistant 消息或浏览器长期存储。
- 状态更新使用节流的 live region，不逐字符打断读屏；折叠按钮具备 `aria-expanded` 与可见焦点。
- reasoning 原始 delta 最多 2,000 字符；服务端脱敏附加截断标记后公共事件契约允许最多 2,048 字符。连续同类分片在展示层合并；单个连续 reasoning 展示块每约 32KiB 按 Unicode code point 安全边界拆成 continuation 行，避免百万字符集中在一个 DOM 节点或拆断 UTF-16 surrogate pair。
- 时间线超过 80 行或 reasoning 总文本超过 128KiB 时使用 `react-virtuoso` 窗口化；工具卡超过 40 个时同样窗口化。只挂载视口附近条目，已展开 Tool 的状态由面板持有，不因虚拟行卸载丢失。
- 运行态处于底部时自动跟随，包括同一 reasoning 行继续增长；用户手动上滚后停止强制跟随。窗口滚动容器保留 `role="log"`/`role="list"`、键盘焦点和可见焦点样式。

后端对 reasoning 正文执行凭据与敏感 URL 脱敏，并限制每个模型 Attempt 最多公开 1,000,000 字符；前端仍把所有文本视为不可信内容。OpenAI Responses 只显示供应商返回的 summary，OpenAI-compatible/Anthropic 则显示其协议实际返回的可见 reasoning。

## 6. 兼容、回滚与验收

- 新事件仍使用 `schemaVersion: '1.0'`。SSE 请求通过 `includeReasoning` 显式订阅：旧客户端缺省 `false` 时，服务端把同序号 reasoning 安全投影为已支持的 `model.activity`；新客户端固定发送 `true`。发布顺序因此为先发兼容后端，再发新前端。
- `model.activity` 只更新运行状态，不进入思考正文时间线，也不显示 `processedCharacters`；终态没有 reasoning 正文时明确说明旧计数无法还原为内容。
- 历史端点是增量能力；旧客户端不调用时仍可用现有 SSE。
- 隐藏 `ThinkingPanel` 只是 UI 回滚，不会删除服务端已持久化的 reasoning。旧 Run 不回填、不构造历史。

验收覆盖：`FULL/SUMMARY` 逐分片拼接、无 reasoning 空态、规划/模型/Tool 交错顺序、实时与历史去重、超过 10k 事件/1k Tool 后仍到达尾页、循环游标与请求失败 partial、长列表 DOM 有界、运行自动跟随与手动上滚、RUNNING/三种终态、刷新恢复、纯文本 XSS canary、键盘和读屏。实现阶段运行 Agent parser/reducer/component 测试、`yarn lint`、`yarn typecheck`、`yarn build` 与 `1440×900` 刷新恢复场景。
