### 为什么选 Vitest 而非 Jest？

- 与 Vite 共享配置（路径别名、SWC 编译），零额外配置
- 原生 ESM 支持，与项目 `"type": "module"` 一致
- HMR 热更新模式，开发体验更快
- API 与 Jest 兼容，迁移成本低

## 三、目录结构与约定

### 3.1 测试文件位置

采用 **`__tests__/` 子目录** 策略，测试文件放在与源文件同目录下的 `__tests__/` 子文件夹，**不与源文件同级放置**：

```
src/
├── utils/
│   ├── format-number.ts
│   ├── format-time.ts
│   └── __tests__/                    ← 测试子目录
│       ├── format-number.test.ts
│       └── format-time.test.ts
├── api/
│   ├── client.ts
│   └── __tests__/
│       └── client.test.ts
├── auth/
│   ├── auth-reducer.ts
│   └── __tests__/
│       └── auth-reducer.test.ts
├── permission/
│   └── __tests__/
│       └── use-permission.test.ts
└── test/                             ← 测试基础设施（setup、工具函数）
    ├── setup.ts                      ← Vitest 全局 setup
    └── test-utils.tsx                ← 自定义 render 和工具
```

测试文件引用源文件时使用相对路径 `../`：

```ts
// ✅ 正确（从 __tests__/ 向上一层）
import { fNumber } from '../format-number';
import { tokenStorage } from '../client';

// ❌ 错误
import { fNumber } from './format-number';
```

### 3.2 命名约定

| 类型       | 文件名格式                        | 示例                        |
| ---------- | --------------------------------- | --------------------------- |
| 单元测试   | `<模块名>.test.ts`                | `format-number.test.ts`     |

| 集成测试   | `<功能名>.integration.test.tsx`   | `auth-flow.integration.test.tsx` |

#### 4.6 测试基础设施增强

Phase 2 涉及组件渲染测试，需要先增强测试基础设施，使组件在接近真实环境中运行。

##### 4.6.1 扩展 `renderWithProviders`（src/test/test-utils.tsx）

当前 `renderWithProviders` 仅包裹 `userEvent.setup()` + `render()`，Phase 2 组件依赖 MUI Theme 和 Router，需增加：

```typescript
// src/test/test-utils.tsx
import type { ReactElement } from 'react';

import { render } from '@testing-library/react';
import userEvent from '@testing-library/user-event';
import { MemoryRouter } from 'react-router-dom';

import { ThemeProvider, createTheme } from '@mui/material/styles';

// 使用默认 MUI 主题即可覆盖大部分组件场景
const defaultTheme = createTheme();

type RenderOptions = {
  route?: string;          // 初始路由路径
  withRouter?: boolean;    // 是否包裹 MemoryRouter（默认 true）
  withTheme?: boolean;     // 是否包裹 ThemeProvider（默认 true）
};

export function renderWithProviders(ui: ReactElement, options: RenderOptions = {}) {
  const { route = '/', withRouter = true, withTheme = true } = options;

  let wrapped = ui;

  if (withTheme) {
    wrapped = <ThemeProvider theme={defaultTheme}>{wrapped}</ThemeProvider>;
  }
  if (withRouter) {
    wrapped = <MemoryRouter initialEntries={[route]}>{wrapped}</MemoryRouter>;
  }

  return {
    user: userEvent.setup(),
    ...render(wrapped),
  };
}

export { render, userEvent };
```

#### 4.7 Label 组件测试（src/components/label/）

> **文件位置**：`src/components/label/__tests__/label.test.tsx`  
> **复杂度**：🟢 低  
> **依赖 Mock**：无（纯样式组件）

**业务背景**：Label 是全局最常用的状态标签组件，在用户列表（Active/Banned）、回测任务（运行中/完成/失败）、策略管理等几十处使用。必须确保不同 variant/color 组合正确渲染，尤其是禁用态不可交互。

| 测试项 | 业务场景 | 验证要点 | 状态 |
| ------ | -------- | -------- | ---- |
| 默认渲染 | 最基本使用 `<Label>text</Label>` | 渲染 span 元素，variant 默认 `soft`，color 默认 `default` | 📋 待实现 |
| 文本首字母大写 | children 为 string 时自动 upperFirst | `"active"` → 渲染为 `"Active"`；ReactNode children 不做转换 | 📋 待实现 |
| startIcon 渲染 | 标签前置图标（如状态指示器） | startIcon 出现在文本前方，不传时不渲染图标容器 | 📋 待实现 |
| endIcon 渲染 | 标签后置图标（如关闭按钮） | endIcon 出现在文本后方，两个 icon 可同时存在 | 📋 待实现 |
| disabled 状态 | 禁用操作时的标签展示 | pointerEvents 为 none，用户点击不可触发事件 | 📋 待实现 |
| className 合并 | 自定义样式类名不覆盖内置类名 | 同时包含 `labelClasses.root` 和自定义 className | 📋 待实现 |
| variant × color 矩阵 | 4 种 variant（soft/filled/outlined/inverted） × 7 种 color | 至少抽检 filled+error、outlined+success、inverted+primary，确保渲染无异常 | 📋 待实现 |

**测试设计示例**：

```typescript
describe('Label', () => {
  describe('文本渲染与首字母大写', () => {
    it('字符串 children 自动首字母大写：active → Active', () => {
      renderWithProviders(<Label>active</Label>);
      // "active" 应被 upperFirst 转为 "Active"
      expect(screen.getByText('Active')).toBeInTheDocument();
    });

    it('ReactNode children 保持原样，不做文本转换', () => {
      renderWithProviders(<Label><span data-testid="custom">custom</span></Label>);
      expect(screen.getByTestId('custom')).toHaveTextContent('custom');
    });
  });

  describe('禁用状态', () => {
    it('disabled=true 时用户无法与标签交互', () => {
      const onClick = vi.fn();
      renderWithProviders(<Label disabled={true} onClick={onClick}>Disabled</Label>);
      // 验证 pointerEvents 被设为 none — disabled 标签不响应点击
      const label = screen.getByText('Disabled');
      expect(label.closest('[class*="Label"]')).toHaveStyle({ pointerEvents: 'none' });
    });
  });
});
```

## 八、最佳实践

1. **测试文件放在 `__tests__/` 子目录** — 不与源文件同级，目录结构清晰，import 用 `../`
2. **每个 `describe` 块对应一个函数或组件** — 结构清晰
3. **使用 `test-utils.tsx` 中的 `renderWithProviders`** — 统一 Provider 包裹
4. **API 测试使用 MSW** — 接近真实网络行为，避免 mock 泄漏
5. **避免测试实现细节** — 测试行为和输出，而非内部状态
6. **保持测试独立** — 每个 test case 不依赖其他 test 的执行顺序
7. **null/undefined/边界值** — 每个函数至少测试边界情况
8. **修改源文件必须同步更新测试** — 新增/修改/删除函数都需同步维护 `__tests__/` 中对应用例
