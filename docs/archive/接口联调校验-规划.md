## 四、每个模块的校验步骤（标准流程）

对每个模块执行以下 6 步：

### Step 1: URL 路径一致性
- 对比前端 `apiClient.post('/api/xxx')` 和 swagger `POST /xxx`
- 修正路径拼写差异

### Step 2: 请求参数字段比对
- 提取 swagger DTO 的所有字段（含 allOf 继承的字段）
- 提取前端 TypeScript 类型的所有字段
- 找出：
  - **前端缺少的必填字段**（🔴 严重 — 请求必失败）
  - **前端缺少的可选字段**（🟡 一般 — 功能可能不完整）
  - **前端多余的字段**（⚪ 低风险 — 后端会忽略）

### Step 3: 字段类型比对
- `string` vs `number` 类型不匹配
- 数组类型 `string[]` vs `string` 不匹配
- 嵌套对象结构比对

### Step 4: 枚举值比对
- swagger 中 `enum` 定义的值与前端传参一致性
- 大小写敏感检查（如 `INDUSTRY` vs `industry`）

### Step 5: 必填/可选标注比对
- swagger `required` 字段 vs 前端类型中 `?` 可选标记
- 前端标记为必填但后端可选的字段（过度约束）
- 前端标记为可选但后端必填的字段（🔴 风险）

### Step 6: 前端未使用的 swagger 字段
- 列出 swagger DTO 中存在但前端类型未定义的字段
- 评估是否需要补充以获得完整功能

## 六、风险评估与注意事项

### 6.1 swagger 响应 DTO 缺失
swagger.json 中 **所有 POST 端点的响应 DTO 均无 `$ref` 引用**（响应 schema 内联或未定义），因此：
- 响应字段校验需要通过实际调用接口对比
- 本次规划主要聚焦**请求参数（入参）**的校验

### 6.2 swagger DTO 字段可能不完整
部分 DTO 的 `properties` 为空（如 `CreatePortfolioDto`、`AddHoldingDto`），这可能是：
- 后端使用了 `@ApiBody()` 但未在 DTO 上添加 `@ApiProperty()` 装饰器
- 需要后端补充 swagger 注解

### 6.3 前端类型可能更宽泛
前端 TypeScript 类型可能定义了比 swagger 更多的字段（用于 UI 状态管理），这些"多余"字段如果不传给 API 则无风险。
