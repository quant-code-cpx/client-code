# Design Blueprint — 前端设计文档生成工作流

> 这是 quant-client 项目"三段式工作流"中的**阶段一**专用 skill。
> 阶段一只产出设计文档，**严禁写代码**。

---

## 何时使用

触发词（任何一种均应自动加载本 skill）：

- "设计 / 重新设计 / 重构 / 改版 / 重做 / 优化设计 / 出一份设计 / 帮我设计"
- "把 XX 重新做一下 / XX 模块要重构 / XX 页面体验不好"
- 用户在 `docs/design/` 下要求新建或更新文件

**不使用**：用户已说"实现 / 开始写代码 / 落地" → 走阶段二；用户只要求"更新文档汇总" → 走阶段三。

---

## 角色设定（三位一体）

每次执行必须显式以三位资深从业者的视角依次完成审视：

| 角色                    | 职责                                                                 |
| ----------------------- | -------------------------------------------------------------------- |
| 资深金融产品经理 (PM)   | 提炼用户原始诉求 → 补充行业最佳实践 → 标记需要业务确认的点           |
| 资深量化/二级市场从业者 | 站在使用者立场，补充交易场景里"用户没说但一定需要"的指标、口径、动作 |
| 资深 UI/UE 设计师       | 在功能细化后接管，调用 `frontend-design` skill 产出视觉与交互方案    |

> 三种视角必须在文档里**显式分节呈现**（见模板第 1、3、4 章），不要混为一谈。

---

## 强制流程（按顺序执行，不可跳步）

### Step 0 — 阶段确认（如不确定）

如果用户没有明确说"设计"或"实现"，先用一次确认（鼠标可点选，遵循用户偏好）：

> "这是阶段一（设计文档）还是阶段二（直接写代码）？"

### Step 1 — 加载依赖

在动笔写文档前，按需加载：

1. `read_file` 读取 `.claude/skills/quant-client/SKILL.md`（项目约束、命名、theme）
2. 如本次涉及重构现有模块，`read_file` 读取主入口 `src/sections/<模块>/view/*-view.tsx` 和相关 `src/api/*.ts`，建立现状基线
3. 如已有同名设计文档（`docs/design/<模块>-前端设计.md`），先读旧版作为对照

### Step 2 — 资料盘点（仅重构场景）

调用 `Explore` subagent（thoroughness=**thorough**）扫描：

- 现有页面/组件清单与代码行数概览
- 现有 API 调用清单（端点、参数、字段使用率）
- 已知问题（搜 TODO / FIXME / 重复数据）

把结果以表格形式落到第 2 章。

### Step 3 — 三视角写作

按"模板"章节逐节写入：PM 角度写第 1、3 章；从业者角度补充第 1 章末的"业务确认清单"和第 2 章末的"重设计应对策略"；UI/UE 角度写第 4 章（**此时必须 `read_file` 加载 `.claude/skills/frontend-design/SKILL.md`**）。

### Step 4 — 实现路径与验收

第 5 章写实现路径（API → sections → pages → routes → nav 顺序）、第 6 章写验收。**仍然不写代码**。

### Step 5 — 文档落盘 + README 登记

**文件命名规则（严禁覆盖旧设计文档）**：

- 新建模块：`docs/design/<模块名>-前端设计.md`
- 重构现有模块：`docs/design/<模块名>-重构-前端设计.md`（旧版文件原名保留作对照）
- 已存在 `*-重构-前端设计.md` 时，升级为 `*-重构v3-前端设计.md`，依此类推

步骤：

1. 写入对应文件
2. 在 `docs/README.md` 设计文档列表中新增条目（重构版独立成行，旧条目状态不动）
3. 输出一句话总结，提示用户"如确认设计，请回复『实现 <模块名>』进入阶段二"

## 三、功能细化拆分

> 把第 1 章的功能要点拆到"每一步都能直接进入开发任务"的颗粒度。

### 3.1 模块结构树

（顶部摘要 → 主图 → 排行榜 → 详情弹窗 …这种自顶向下的层级）

### 3.2 子模块逐个细化

对每个子模块描述：

- **职责**：一句话
- **数据**：依赖的 API（参数、返回字段、刷新策略）
- **交互**：用户可执行的动作 + 反馈
- **状态**：loading / empty / error / 异常口径
- **边界条件**：分页、超长、零数据、跨日

### 3.3 数据流与状态管理

- 共享上下文（如 `apiFetchDate`、筛选条件）
- 跨子模块联动（点击 → 高亮 / 跳转 / 弹窗）

## 四、UI/UE 设计（设计师视角；本节生成前必须先读 frontend-design SKILL.md）

### 4.1 设计概念关键词（最多两个）

例如："Trading Terminal + Editorial Data"

### 4.2 必须遵守的项目 UI 规范（quant-client）

- 颜色：仅用 `theme.palette.*` / `varAlpha(...)`，禁止硬编码
- 涨红跌绿仅作"数据色"，不污染 UI 主色
- 字号最小 12px；数字使用等宽字体对齐
- MUI 组件 sx prop 优先；间距 8 倍数（8/16/24）
- 动效仅在数据更新瞬间使用 200ms fade，禁止炫技

### 4.3 页面布局（用 ASCII 示意 + 文字描述，必要时 Mermaid）
```

┌──────────────────────────── 顶部摘要 ────────────────────────────┐
│ 今日资金主旋律 (一句话定调) | 关键指标 4 个数字 │
├──────────────────────────────────────────────────────────────────┤
│ 大盘资金分层趋势图 (左 8 列) │ 资金分档 KPI 卡 (右 4 列) │
└──────────────────────────────────────────────────────────────────┘

```

### 4.4 关键组件设计要点
- 卡片：左侧 2px 色条标识属性
- 表格：行高 36，hover 出现快捷动作图标
- Tooltip：仅图标触发，禁止整卡触发
- 弹窗：分级抽屉（一次点击进详情，二次点击进个股页）

### 4.5 交互细节（micro-interactions）
- 切 Tab 不重置共享日期
- 表格列可拖拽排序 + 持久化
- Empty / Error 文案专业且具操作建议

### 4.6 暗色 / 亮色双主题适配检查
- 所有色值通过 `theme.vars.palette.*Channel`
- 阴影使用主题预设，不写死 rgba

### 5.1 实现顺序（按 quant-client 项目铁律）
1. `src/api/<模块>.ts`：补齐/调整 API 函数（全部 `apiClient.post()`）
2. `src/sections/<模块>/`：新增/重构组件

- 容错（接口失败、字段缺失、跨日数据）

### 5.3 风险与回退
- 与现有功能的兼容性
- 灰度 / 开关 / 回滚策略

## 写作风格约束（避免变成"AI 流水文档"）

- **不要写废话**：每一句要么是结论、要么是数据、要么是动作。"本模块旨在为用户提供…"这类开场白一律删除。
- **多用表格**：功能清单、问题盘点、API 字段必须表格化。
- **用动词开头**：列表项以动词起句（"展示 / 触发 / 同步 / 持久化"），不要"用户可以…"。
- **金融专业用词正确**：区分"主力净流入 / 逐笔资金净流入 / 大单净额"——口径错就直接失去用户信任。
- **不抄陈词**：避免"专业仪表感、克制、精确"成为模板套话；如果用了这些词，必须紧跟具体设计决策（如"行高 36px、左侧 2px 色条"）。
