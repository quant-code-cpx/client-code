# Desktop UI Reverse

从可核验材料还原目标界面的真实规则，再把规则映射到当前 React/MUI 工程。范围固定为 PC 桌面浏览器，覆盖鼠标、键盘、桌面宽度适配、主题和视觉验收。

## 证据纪律

所有结论必须标为以下一种，不得混写：

- **已测量**：截图、DOM、computed styles、源码、资源、网络或实际交互可直接确认。
- **有依据的推断**：由多个页面、组件、状态或桌面宽度共同支持，并写明推理链。
- **暂时假设**：材料不足时用于继续分析的默认值；写明风险、替换条件和所需证据。

禁止凭截图猜字体、资源、断点、交互结果、兼容性、性能或品牌规范。无法访问目标、资源缺失或状态不可操作时，准确记录阻塞点和需要补充的材料。

## 强制阶段门禁

新目标首次进入时：

1. 读取用户提供的全部页面、截图、录屏、源码、资源和现有代码约束。
2. 可运行时检查 DOM、computed styles、CSS variables、字体与图片请求、资源固有尺寸、媒体查询和实际交互。
3. 只交付“复刻范围与材料清单”“证据与风险清单”“页面地图与布局关系”，可附关键 token 线索，但不建立最终组件系统，不写最终页面代码。
4. 等用户确认页面范围、关键视觉线索和风险后再继续。若用户已明确确认过，或明确要求跳过该门禁，记录依据后进入后续阶段。

材料不足不使用通用模板补空。应继续完成可确认部分，并列出阻塞后续工作的最小补充材料。

## 后续工作流

用户确认后，完整读取 [references/桌面端UI逆向规范.md](references/桌面端UI逆向规范.md)，按其顺序完成：

1. 提取 primitive、semantic、component 三层 tokens。
2. 建立资源清单、组件目录、受约束 API 和完整状态矩阵。
3. 归纳超宽、标准、紧凑桌面宽度下的内容驱动变化及主题规则。
4. 先复用项目 theme、组件和资源，再提出新建项；不得建立平行设计系统。
5. 按骨架、tokens、组件状态、真实资源、交互与性能顺序实现，每阶段运行并检查。
6. 使用固定环境的目标/实现截图、overlay、pixel diff、DOM/computed diff 和真实交互完成分层验收。

进入当前项目实现时，叠加 `$quant-client` 与 `$quant-ui-design`；进入浏览器回归时叠加 `$frontend-qa`。只在对应阶段读取这些 skill，不提前加载无关流程。

## 实现原则

- 先分析后实现，先复用后新建，先保真后抽象。
- 不用通用字体、Unicode 符号、随机图标、占位图片或默认渐变冒充真实资源；替代项必须列明原因和视觉风险。
- 状态证据至少检查 default、hover、focus-visible、active、pressed、selected、disabled、loading、error、empty 和 expanded；适用时补 checked、success、stale、partial、dragging。
- 保持目标视觉语言，但修复键盘不可达、焦点不可见、弹窗焦点逃逸、对比度不足和错误信息未关联等明显缺陷，并记录偏离目标的原因。
- 多处值不一致时，先判断组件变体、桌面宽度、主题、状态或局部例外，不取平均值制造规则。
- 视觉参数和业务数据分离；组件 API 使用有限、语义化的 `variant`、`size`、`state`、`density`、`tone`、`loading`、`disabled`、`fullWidth` 等参数。

## 完成标准

- 每个关键结论有来源、环境和证据等级。
- 页面地图能表达父子关系、阅读顺序、对齐线、容器、固定或流式尺寸、sticky 与 overflow。
- tokens、资源和组件状态均可追溯到证据；替代与例外单独记录。
- 桌面宽度、主题、鼠标、键盘、缩放、对比度、焦点和 reduced-motion 均有验收结果。
- 未解决问题、暂时假设和人工确认项没有被包装成已完成。
