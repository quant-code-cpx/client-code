文件与接口只是数据交换链的不同载体；扩展名、HTTP 200 或校验和相同，都不能单独证明数据已被正确解释。下面用一个完全虚构的“日行情快照”贯穿全页：研究客户端通过 HTTPS API 分页取得清单，下载 CSV/GZIP 或 Parquet 文件，核对原始字节摘要，再按固定字符编码、模式与快照标识流式解析。

```json
{
  "dataset": "daily-prices",
  "schema_version": "2.0.0",
  "snapshot_id": "snap-20260813T080000Z",
  "as_of": "2026-08-13T08:00:00Z",
  "files": [
    {
      "path": "trade_date=2026-08-13/part-000.parquet",
      "format": "parquet",
      "compression": "zstd-internal",
      "bytes": 123456,
      "sha256": "<64 lowercase hexadecimal characters>"
    }
  ],
  "next_cursor": "opaque-cursor-example"
}
```

末页应返回 JSON 字面量 `null`，而不是字符串 `"null"`。对应数据模式约定：`trade_date` 是无时区日历日期；`symbol` 是非空 UTF-8 标识；`close` 是币种 CNY、精度 4 位小数的十进制数；`volume` 是非负 64 位整数；`source_updated_at` 是带明确 UTC 偏移的 RFC 3339 时间戳（本例用 `Z`）。清单中的路径、摘要和数量均为教学占位，不对应真实服务。

## 文本文件 {#text-files}

磁盘和网络保存的是字节；“文本”是用字符编码把字节解释为 Unicode 字符后的结果。`.txt` 扩展名既不指定编码，也不指定列、数据类型、换行或缺失值。接收文本文件时至少要冻结编码、换行、记录边界、字段语法和文件是否允许末尾缺换行。

同一视觉文本可以有不同字节，同一字节在不同编码下也可解出不同字符。`LF`、`CRLF` 与旧式 `CR` 是不同换行序列；以二进制摘要核对时它们不等价。文本模式 I/O 还可能做换行转换，因此应先明确校验的是传输原始字节，还是规范化后的逻辑内容。

“一行一条记录”只在格式保证字段内部不能含换行时成立。CSV 的带引号字段可以含换行；JSON 单个顶层文档也可跨多行。用普通 `splitlines()` 解析这些格式会把展示行误当记录边界。固定宽度文本又需要按字节宽度还是字符宽度解释；UTF-8 中文字符占多个字节，二者不能混用。

文本适合可读日志、小型清单和跨工具交换，但不自动携带强类型、索引或业务模式。原始文件、解析参数和模式版本应一起留存，不能只保留“已读成表”的结果。

## CSV {#csv}

CSV 是表格交换的常见文本形式，却存在多种方言。IETF [RFC 4180](https://www.rfc-editor.org/rfc/rfc4180.html)只是记录常见格式并注册 `text/csv` 的 Informational RFC，不是让所有 `.csv` 自动服从同一强制标准。生产者和消费者必须另行约定分隔符、引号、转义、换行、表头、空值与编码。

在 RFC 4180 常见方言中，字段由逗号分隔；包含逗号、双引号或换行的字段要用双引号包围，字段内双引号写成两个双引号：

```csv
trade_date,symbol,note,close
2026-08-13,ALPHA,"revised, source said ""final""",10.2500
```

这里第三列仍是一个字段。不能用字符串 `split(",")`；应使用支持所选方言的 CSV 解析器。在 Python 标准库中，官方 [`csv` 文档](https://docs.python.org/3.14/library/csv.html)建议文本文件显式指定编码并以 `newline=""` 打开，让 CSV 模块自行处理嵌入换行。

CSV 没有内建类型：`00123` 是标识还是整数、空字段是空字符串还是缺失、`1,234` 是一个带千分位的数还是两列，都由外部模式决定。日期、时区、币种和小数精度也不会随文件传递。表头可缺失、重复或改名，列顺序变化不能静默按旧位置解析。

CSV 本身是数据，但电子表格可能把以特定字符开头的单元格解释为公式。若文件将被不可信来源与电子表格共同使用，要依据目标应用的官方安全规则处理，不能把加引号当作通用防护，也不能改坏原始值而不留审计副本。

## JSON {#json}

JSON 只有对象、数组、字符串、数值、布尔和 `null` 六类值，没有日期、十进制金额、字节串或时区类型。对象成员顺序不具业务语义，数组顺序才有语义；对象名称应唯一，因为重复名称在不同解析器中可能报错、保留首个、保留末个或保留全部。

本例清单把 `as_of` 写成 RFC 3339 字符串，并显式带 `Z` 表示 UTC。仅写 `"2026-08-13 08:00:00"` 无法确定时区；日期 `trade_date` 与时间戳是不同对象。`null` 表示成员存在且值为空，成员缺失表示没有提供，更新语义中二者不能合并。

JSON 数值语法不规定实现必须使用何种机器精度。RFC 8259 指出，整数落在 $[-(2^{53}-1),2^{53}-1]$ 时，不同采用 IEEE 754 binary64 的实现更可能精确一致；更大整数和高精度小数可能被舍入。本例可把 `close` 作为有模式约束的十进制字符串，或传整数最小货币单位并同时给比例，不能假设 `10.2500` 的尾随零和十进制精度会被所有语言保留。

标准 JSON 不包含 `NaN`、`Infinity` 或 `-Infinity`。某些库默认接受扩展值，跨系统前要启用严格模式。开放生态交换的 JSON 文本必须使用 UTF-8，发送方不得加 BOM；接收方可为互操作选择忽略 BOM，但不应把宽松接收变成生产格式。正式边界见 [RFC 8259](https://www.rfc-editor.org/rfc/rfc8259.html)与时间戳规范 [RFC 3339](https://www.rfc-editor.org/rfc/rfc3339.html)。

## Parquet {#parquet}

Apache Parquet 是面向分析的列式二进制文件格式。文件由一个或多个 row group 组成；每个 row group 对每列有一个连续 column chunk，column chunk 再分成 page，page 是编码与压缩的基本单位。读取少数列时可跳过无关 column chunk，按统计元数据做谓词裁剪则取决于文件是否有相应元数据以及读取引擎是否正确使用，不能把“Parquet”三个字等同于查询必然更快。

本例的 `close` 应写为带精度/标度的 DECIMAL 逻辑类型，`source_updated_at` 要冻结时间单位与 UTC 调整语义；把两者都写成普通字符串会失去列式类型优势。Parquet 文件包含结构模式，但“价格非负、币种为 CNY、主键唯一”等业务约束仍需外部数据契约。

Parquet 适合按列扫描和批量分析，不适合频繁原地更新单行。row group 太小会增加元数据与调度开销，太大又提高读取和峰值内存；应按对象存储、查询列和工作负载测量，而不是套固定行数。字典编码对低基数列可能有效，高基数时实现可回退，不能假设每列都使用字典。

目录 `trade_date=2026-08-13/` 是数据集分区约定，不属于单个 Parquet 文件值的自动真相。分区目录与文件内 `trade_date` 冲突时必须按契约报错，不能任意选一个。Apache 官方的[格式概念](https://parquet.apache.org/docs/concepts/)与[压缩规范](https://parquet.apache.org/docs/file-format/data-pages/compression/)定义了 row group、column chunk、page 及受支持编码边界。

## 压缩 {#compression}

压缩减少字节，不提供保密性，也不自动提供来源真实性。`daily.csv.gz` 是整个 CSV 经 GZIP 外层压缩；Parquet 则通常在 page 内使用 ZSTD、GZIP、Snappy 等 codec。两种压缩层级的随机访问、并行度和摘要对象不同，清单必须说明 codec、层级和参数。

压缩、归档和编码也不同：GZIP 通常压缩一个字节流，ZIP/TAR 可容纳多个命名条目，Base64 是可逆编码而非压缩。HTTP `Content-Encoding: gzip` 描述传输内容编码，文件名 `.gz` 描述被保存的对象约定；客户端库自动解压后，调用者拿到的字节可能已不是线上内容，计算摘要前要确定层级。

压缩率是数据相关的。下载大小为 100 MB、解压后 5 GB 时，若程序只按压缩大小设限仍可能耗尽磁盘或内存；嵌套归档和极端高压缩内容要同时限制压缩字节、解压字节、条目数、单条目大小、递归层数和耗时。部分数据损坏可能直到流尾校验才发现，不能因为前几批能读就提交完整快照。

压缩选择需权衡网络、存储、CPU、可拆分性和兼容性。重复对已压缩 Parquet 再做整文件压缩未必节省空间，反而可能破坏范围读取。清单中 `zstd-internal` 明示本例压缩发生在 Parquet page，而不是把文件再包成 `.zst`。

## 字符编码 {#character-encoding}

字符编码定义 Unicode 码点和字节之间的映射。UTF-8 与 UTF-16 都能表示 Unicode，但同一字符串的字节完全不同；未声明编码时依赖操作系统默认值会使同一脚本在另一环境失败。数据契约应直接写 `UTF-8`，解析器以严格错误策略开始，并把无法解码的原始字节隔离。

用替换字符 `�` 忽略解码错误能让流程继续，却可能合并证券代码、破坏主键或掩盖截断。若业务允许修复，需记录原始字节、错误偏移、采用的回退编码和修复规则。BOM 是编码签名的一种约定，不应当作所有文本必备前缀；RFC 8259 对网络 JSON 明确禁止发送 BOM。

Unicode 视觉相同不保证码点序列相同，例如预组字符与字母加组合符。Unicode [UAX #15](https://unicode.org/reports/tr15/)定义 NFC、NFD、NFKC、NFKD 规范化形式。是否规范化必须由字段语义决定：人名检索可能希望规范化，法律标识、签名输入和外部主键则不能无条件改变。兼容规范化还可能折叠有意义的字符差异。

解码后还要处理换行和区域规则。大小写转换、全半角、空白剔除、数字小数点都不是字符编码的一部分。编码成功只说明字节可映射为字符，不说明字符串满足模式或代表正确证券。

## 模式 {#schema}

模式（schema）是数据结构和约束的可版本化契约，不只是列名清单。本例至少要规定：

| 字段 | 逻辑类型 | 可空 | 单位/约束 |
| --- | --- | --- | --- |
| `trade_date` | date | 否 | 交易所日历日期 |
| `symbol` | UTF-8 string | 否 | 非空；与市场共同构成键 |
| `close` | decimal(18,4) | 是 | CNY/股；停牌缺值保留 null |
| `volume` | int64 | 否 | 股；$\ge0$ |
| `source_updated_at` | timestamp(us, UTC) | 否 | 源版本时点 |

还要写主键、重复处理、排序是否有保证、缺失与零的区别、允许枚举、时间有效性和字段血缘。`schema_version="2.0.0"` 只在发布者给出兼容规则时才有意义；增加可选字段、改变可空性、扩大数值范围、改单位或重命名列对不同消费者的破坏程度不同。

JSON Schema Draft 2020-12 可描述 JSON 类型、必需成员、范围和组合条件，但 `format` 在不同词汇配置下可能只是注解而非强制断言，必须核对验证器配置。CSV 需要外部 schema，Parquet 内嵌物理/逻辑类型仍不覆盖全部业务规则。官方 [JSON Schema 2020-12](https://json-schema.org/specification)把 Core 与 Validation 词汇分开。

通过模式只说明结构满足所写断言，不证明行情真实、快照完整或字段经济含义正确。模式升级要同时保留生产者版本、消费者兼容矩阵、迁移规则和失败样本，不能在解析器里悄悄把未知字段丢掉。

## 序列化 {#serialization}

序列化把内存对象变成可交换表示；它必须选择哪些类型信息保留、如何编码以及是否要求确定性。同一个逻辑对象可以序列化为不同但合法的 JSON：空格、转义、对象成员顺序和数值文本都可不同，所以原始字节摘要不同并不必然代表逻辑内容不同。

本例从精确十进制 `10.2500` 写 JSON 时，若转成二进制浮点再输出，可能丢失标度；可写为模式规定的字符串 `"10.2500"`，或写整数 `102500` 并声明比例 $10^{-4}$。时间戳统一输出 RFC 3339 UTC，如 `2026-08-13T08:00:00Z`，不能依赖本机时区。缺失字段、显式 `null` 和业务零分别处理。

CSV 序列化必须按固定方言引用字段并固定列顺序；Parquet 序列化要固定逻辑类型、row group、codec 和格式兼容目标。排序行会产生更稳定输出和可能更好压缩，却改变原始顺序语义，必须在契约中写明。

若要对逻辑对象签名或做跨实现摘要，需要先选正式的规范化表示；简单“JSON 排序键”未必处理数值、Unicode 和转义的全部差异。可复现研究通常同时保存原始交换字节与规范化表，分别回答“收到的是否同一对象”和“解释后的数据是否同一版本”。

## 反序列化 {#deserialization}

反序列化把不可信字节转换为程序对象，是数据交换链的重要安全边界。推荐顺序是：限制传输大小并取得原始字节；核对适用层级的摘要；按上限解压；严格解码；用限定深度、字段数、字符串长度和数值范围的解析器读取；再执行结构模式和业务规则。

解析成功不等于安全或正确。深度极大的 JSON、巨型整数、重复键、高压缩输入和异常数量的 CSV 列都可能消耗资源；Parquet footer 与 page 元数据也不可在验证前完全信任。批次中途失败时，应把整批标为不完整，或使用明确的逐记录容错契约，不能静默提交已读前半段。

不要对不可信来源使用会构造任意语言对象或执行还原钩子的格式。Python 官方 [`pickle` 文档](https://docs.python.org/3.14/library/pickle.html)明确警告不要反序列化不可信或可能被篡改的数据；即使附带普通哈希，只要预期哈希也可被攻击者替换，就没有解决真实性问题。

反序列化还必须保留可追溯性：原始对象 URI、ETag/版本、快照、下载时点、解析器与 schema 版本、拒绝原因和行号。把错误值自动转成 `null` 会把“源确实为空”与“客户端无法解析”混成一种状态。

## 文件路径 {#file-paths}

相对路径相对于当前工作目录或明确基目录解析；绝对路径从文件系统根、盘符或网络共享锚点开始。同一个相对路径在任务调度器、交互终端和容器内可能指向不同位置，所以清单路径应相对于固定数据集根，并把根作为配置记录。URL、对象存储 URI 与本地路径是不同命名空间，不能用字符串替换斜杠互转。

清单中的 `path` 属于外部输入。防御性做法是拒绝绝对路径和不允许的组件，把候选路径解析后验证仍位于允许根目录内：

```python
from pathlib import Path

root = Path("/srv/research/raw").resolve()
candidate = (root / manifest_path).resolve()
candidate.relative_to(root)  # 不在 root 下会抛 ValueError
```

只检查字符串是否以根路径开头不安全，因为相似前缀、父目录组件、大小写规则和符号链接会改变实际目标。上述示例也不是完整的竞态防护：验证后到打开前，符号链接可能变化；高风险写入应使用平台提供的目录句柄、禁止跟随链接、原子创建和权限隔离，并对归档内每个条目重复验证。

`Path.resolve()` 会消除 `..` 并解析可见符号链接，但不存在目标、权限、Windows 盘符/UNC 和大小写语义要分别处理。不要把用户给出的路径直接拼到命令行或日志而不转义。Python [`pathlib` 文档](https://docs.python.org/3.14/library/pathlib.html)说明了纯词法路径与实际解析的差异；MITRE [CWE-22](https://cwe.mitre.org/data/definitions/22)定义了路径限制不当的风险。

## 流式读取 {#streaming-reads}

流式读取让程序一次处理一个记录批次，而不是把整个对象展开到内存。若每批 $c$ 行、每行解析后平均占 $b$ 字节、对象与缓冲开销倍数为 $f$，批次数据本身的粗略内存估算为

\[
M_{\text{chunk}}\approx c\times b\times f,
\]

还要加解压缓冲、解析器状态、输出批次和运行时开销。把 500 万行一次读入与按 20,000 行处理的峰值差异可能很大，但单个超大字段仍能击穿批次上限。

CSV 应让 CSV 解析器读取流，不能按物理行切块，因为引号字段可跨行。单个顶层 JSON 没有天然的逐记录边界；可由 API 分页、使用正式约定的记录分帧格式，或用支持增量解析的实现，不能把任意多行 JSON 当“每行一个对象”。Parquet 常按 row group 或 record batch 读取，并可能先访问 footer；远程读取是否支持范围请求与谓词下推取决于存储和引擎。

流式管线要有背压：下游写入慢时，上游不能无限预取。摘要可随原始字节增量计算，但只有读到流尾并匹配清单后才能确认完整；中途已处理批次应放在暂存事务或与快照完成标记隔离。重启要记录已确认边界，不能从任意压缩字节偏移继续。

峰值内存降低不代表总成本降低。过小批次增加网络、系统调用和提交开销；过大批次增加延迟与失败重做量。选择批次大小应记录数据分布和测量条件，不使用“每次一万行”之类无口径常数。

## 应用程序接口 {#application-programming-interfaces}

应用程序接口（API）是请求、响应、身份和状态变化的契约，不等于某个 URL。HTTP API 至少要冻结方法、目标 URI、查询/正文、`Content-Type`、认证方式、状态码、错误结构、版本和超时。HTTPS 保护传输连接，仍需校验证书、授权范围和返回内容。

本例用安全且幂等的 `GET` 获取清单和文件。HTTP 的“安全”表示客户端没有请求且不预期产生状态改变（日志等附带影响不改变其安全语义），“幂等”表示重复相同请求的预期效果与一次相同；PUT、DELETE 语义上幂等但不安全，重复响应状态不必逐字相同，POST 通常不保证幂等。具体 API 若偏离标准语义，必须按其契约处理。

状态码只描述 HTTP 层：200 表示请求成功处理但仍要核对媒体类型、schema 和业务完整性；202 表示已接受，不代表后台任务完成；204 不应期待消息内容；206 是部分内容；400 系通常要求修正请求或权限，500 系表示服务端失败但也未必都适合重试。重定向还可能改变主机，认证头不能盲目转发。

Bearer token 能持有者即使用，应只在受保护连接和授权头中发送，避免放入 URL、普通日志或错误文本；认证成功也不等于获准访问所有数据集。API 返回的下载 URL、分页链接和文件路径仍是外部输入。HTTP 语义以 [RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html)为准，Bearer token 边界见 [RFC 6750](https://www.rfc-editor.org/rfc/rfc6750.html)。

## 请求限速 {#rate-limiting}

请求限速可能按账户、令牌、IP、端点、并发数、数据行或成本单位计费，并同时存在秒、分钟和日窗口。看到“100 次/分钟”不能推断允许瞬间并发 100；固定窗口、滑动窗口、漏桶和令牌桶的突发行为不同。

令牌桶可用容量 $B$、补充速率 $r$ 个令牌/秒、每次成本 $c$ 表示：最多突发约 $\lfloor B/c\rfloor$ 次，长期平均速率不超过 $r/c$ 次/秒，前提是这正是服务端算法。客户端应在全部工作进程间协调预算，并预留时钟偏差、并发在途请求和其他消费者。

HTTP 429 表示在一段时间内请求过多；响应可以带 `Retry-After`，其值可能是等待秒数或 HTTP 日期。客户端应优先遵守服务契约和该字段，不用高频探测“是否恢复”。配额剩余提示不是服务等级保证，成功响应也可能消耗不同数量的额度。

动态效力边界很重要：截至 2026-08-14，IETF `RateLimit`/`RateLimit-Policy` 通用字段仍是 [Internet-Draft](https://datatracker.ietf.org/doc/draft-ietf-httpapi-ratelimit-headers/)，尚非最终 RFC；大量服务仍使用各自字段和语义，不能把某家 `X-RateLimit-*` 解释套到所有 API。现行标准基础是 [RFC 6585](https://www.rfc-editor.org/rfc/rfc6585.html) 的 429 与 RFC 9110 的 `Retry-After`。

## 分页 {#pagination}

分页把结果集拆成多个响应。页码/偏移分页易跳转和估算，但在数据持续插入、删除或重排时，后续偏移会重复或漏掉记录；游标分页把位置或快照状态编码成不透明令牌，通常更适合变化数据，但客户端不得解析或修改游标。

若固定快照确有 $N=237$ 条且服务端接受每页 $p=100$，请求数为

\[
\left\lceil\frac{N}{p}\right\rceil=3.
\]

这只在总数准确、快照不变且每页上限稳定时成立。短于页大小的一页不一定是最后一页；应以契约中的 `next_cursor=null` 或正式 `next` 链接结束。RFC 8288 的 [Web Linking](https://www.rfc-editor.org/rfc/rfc8288.html)可表达 `rel="next"`，但具体 API 也可在 JSON 正文提供游标。

为保证一致性，本例每一页必须携带同一个 `snapshot_id`，排序键需稳定且有唯一决胜字段，例如 `(trade_date, market, symbol)`。恢复任务要保存“已持久化页对应的下一个游标”和快照，不能只保存页号。用主键去重能消除部分重复，却不能发现被分页漂移漏掉的记录。

分页响应还要核对页面内重复、跨页重复、游标循环、快照变化、总数变化和最后完成标记。并行抓取任意页可能打破服务端顺序与速率契约；游标链通常必须顺序取得，除非接口明确提供可并行分片。

## 重试 {#retries}

网络超时意味着客户端“不知道结果”，不等于服务器没有执行。自动重试应限于安全或幂等操作，或服务明确提供、且客户端稳定复用的幂等键。对创建订单、扣费等非幂等 POST 盲目重试可能重复产生状态；换一个新幂等键同样失去去重作用。

可重试条件要按接口定义。连接中断、408、429、502、503、504 有时适合重试，但请求正文是否已发送、服务器是否处理、响应是否带 `Retry-After` 都会改变决策；400、401、403 等通常应先修正输入或凭证。501 等永久能力错误不应反复请求。重试不能绕过权限、限速或业务拒绝。

指数退避加 full jitter 可写为

\[
D_k=\min(D_{\max},D_0 2^k),\qquad
W_k\sim\operatorname{Uniform}(0,D_k),
\]

其中 $k=0,1,\ldots$ 是失败序号，$E[W_k]=D_k/2$。若服务给出可信 `Retry-After`，应按服务契约至少等待其指示时间；同时仍设置总截止时间、最大尝试次数和重试预算。随机抖动降低许多客户端同时重试的同步峰值，但不能保证服务恢复。

每次尝试要记录请求标识、幂等键、状态、耗时和最终结果，敏感凭证除外。重试层只能位于一个明确位置；SDK、代理和业务代码各重试三次可能把一次调用放大成 $3^3=27$ 次。熔断、并发削减和失败快速返回是不同机制，不能全部叫“重试”。

## 校验和 {#checksums}

校验和或摘要把字节序列映射为固定长度值。本例清单约定对**下载到的原始文件字节**计算 SHA-256：

\[
h=\operatorname{SHA256}(b_0\Vert b_1\Vert\cdots\Vert b_{m-1}).
\]

必须同时记录算法、输入层级和摘要编码。对 `.csv.gz` 的压缩字节、解压 CSV 字节和规范化换行后的文本计算会得到三个不同摘要；都可能有用，但回答的问题不同。流式计算可减少内存，只有读到末尾并比对成功才能确认这份字节完整。

普通哈希可高概率发现偶然损坏和与可信预期值不一致的修改，却不证明发布者身份。如果攻击者能同时替换文件与清单中的摘要，二者仍会匹配；真实性需要从独立可信渠道取得摘要，或使用带密钥的 MAC、数字签名和受保护的密钥/证书链。CRC 适合传输差错检测，不应冒充抗恶意篡改的密码学证明。

HTTP [RFC 9530](https://www.rfc-editor.org/rfc/rfc9530.html)区分对消息内容的 `Content-Digest` 和对表示数据的 `Repr-Digest`，两者不能按旧 `Digest` 字段随意互换。SHA-256 算法定义见 NIST [FIPS 180-4](https://csrc.nist.gov/pubs/fips/180-4/upd1/final)。即使摘要、schema、行数全部通过，也只证明对应技术约束；它们不证明数据无遗漏、经济含义正确、来源独立或事实真实。

**规范与动态边界（核对至 2026-08-14）：**CSV 依据 RFC 4180 的 Informational 定位；JSON 依据 RFC 8259、时间戳依据 RFC 3339；Parquet 依据 Apache 当前格式规范；字符规范化依据 Unicode 17.0 的 UAX #15；JSON Schema 采用当前 Draft 2020-12；HTTP 方法、状态与 `Retry-After` 依据 RFC 9110，429 依据 RFC 6585，分页链接依据 RFC 8288，摘要字段依据 RFC 9530，SHA-256 依据 NIST FIPS 180-4。`RateLimit` 字段明确仍为 2026 年在途草案，未作为现行 RFC。全部接口、路径、数值和对象均为虚构教学材料。
