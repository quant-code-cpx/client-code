量化研究的结果不是由“代码”单独生成，而是由代码、依赖、配置、数据、参数、运行环境和执行过程共同生成。本页用一个虚构研究项目贯穿：`momentum-lab` 读取截至 2026-08-13 可得的日频价格快照，计算 20 日动量，使用 2021—2024 年形成规则、2025 年作样本外评价，并输出收益序列、指标表和研究报告。

一次运行的证据链可先概括为：

\[
\text{代码版本}+\text{依赖与系统环境}+\text{配置}+\text{数据快照}+\text{参数与随机状态}
\xrightarrow{\text{运行清单}}
\text{制品与指标}.
\]

若其中任何一环只写“用最新版”“取当时数据”或“参数同上”，未来就可能无法解释结果差异。以下所有标识和数字均为教学示例，不对应真实证券、仓库或数据服务。

## 版本控制 {#version-control}

版本控制系统记录文件状态及其演变，使研究者能够定位“当时究竟使用了哪份代码”。在 Git 中需要分清四层：

| 层次 | 含义 | 是否自动进入提交 |
| --- | --- | --- |
| 工作区 | 当前磁盘上的文件 | 否 |
| 暂存区/索引 | 下一次提交拟包含的快照 | 提交时进入 |
| 提交对象 | 一个目录树快照、父提交、作者/提交者信息和消息 | 已固定为对象 |
| 引用 | 分支、标签、远端跟踪分支等指向对象的名称 | 可移动 |

因此“项目在 Git 里”不等于运行可追溯。若研究从有未提交改动或未跟踪文件的工作区启动，只记录 `HEAD` 会指向另一份代码。严谨做法是要求正式运行使用干净快照，或同时保存未提交补丁及其内容摘要，并明确标记 `dirty=true`。

Git 对象 ID 是按仓库所用对象格式计算的内容寻址标识。它能精确定位对象，但不自动证明代码正确、来源可信或没有被恶意提交。签名还需要可信密钥、验证策略、吊销状态和托管流程，不能把“有哈希”误写成“内容真实”。

版本控制也不适合直接存放大型受限数据、凭据或可识别个人信息。研究链应在代码仓库中保存数据引用、模式和快照摘要，在获授权的数据系统中保存受控数据本体。

## 提交 {#commits}

一个 Git 提交是所指目录树的快照，并记录父提交、作者、提交者、时间和消息。它不是“差异文件”；差异是比较两个快照后计算出来的视图。统一项目的一次研究提交应尽量构成可解释的逻辑单元，例如：

```text
research: define 20-day momentum using adjusted close

- exclude the current day from the 20-session lookback
- reject securities with fewer than 21 valid observations
- record adjustment-method version in the run manifest
```

消息应说明为什么改变、影响哪个口径和如何迁移，而不只写“fix”。但提交消息、作者名和时间通常是提交者提供的元数据，并非独立事实证明；提交历史也可能经 amend、rebase 或过滤而改写，改写会产生新的对象 ID。

正式运行要记录完整对象 ID，而不是只记录可能碰撞或歧义的短前缀。还应记录仓库身份、子模块或外部源码的精确版本。提交足够小有助于审查与回退，但“每行一个提交”会破坏语义完整性；边界应以可独立理解和验证为准。

一个提交能证明仓库保存了什么，不能证明该代码被运行过。运行证据还要把提交 ID 与数据、环境、参数、入口和输出连接起来。

## 分支 {#branches}

Git 分支是指向某个提交的**可移动引用**。新提交产生后，当前分支通常前移；所以仅记录 `main`、`research` 或“发布分支”不能固定一次历史运行。标签也只是引用：轻量标签直接指向对象，附注标签另有标签对象、消息并可签名，但引用本身仍可能被有权限者重建或删除。

统一项目可以这样分工：

- `main` 表示团队当前认可的基线；
- 短期研究分支承载一个可审查假设；
- 受保护的发布标签标记冻结版本；
- 运行清单始终记录最终提交对象 ID，而非只记录分支或标签名称。

分支方便并行开发，不是进程、权限或数据隔离边界。两个分支可能读取同一可变数据库并覆盖同一路径；敏感研究仍需独立权限、命名空间和输出目录。

合并提交、压缩合并和变基具有不同历史形态，但研究可复现性的核心仍是“最终快照是什么、如何审查、运行引用哪个对象”。不要从一条整洁提交线推断研究过程没有试错、遗漏或选择性报告。

## 变更记录 {#changelog}

提交历史面向开发者记录细粒度演变，变更记录面向使用者说明语义影响，二者不可互相替代。一次动量研究的变更记录应回答：

| 字段 | 示例 |
| --- | --- |
| 版本/生效日期 | `model-2.1.0 / 2026-08-14` |
| 变更 | 回看窗口从 20 个自然日改为 20 个有效交易日 |
| 原因 | 原口径在跨节假日时实际观察数不一致 |
| 影响范围 | 特征、换仓日信号、历史回测均受影响 |
| 是否重算 | 从数据快照 `cn-eod-20260813-v3` 全量重算 |
| 迁移/兼容 | 旧制品保留为 `method=calendar-v1`，不可直接拼接 |

版本号可以采用 SemVer，但前提是项目先定义“公共接口”。MAJOR/MINOR/PATCH 表达的是发布者承诺的兼容性，不是改动规模、正确性或风险等级；研究方法变更即使只改一行，也可能令历史指标不可比。零主版本、预发布标记和项目自定义版本策略要另行说明。

变更记录是人工维护的摘要，可能遗漏或写错。它应链接到提交、议题、数据迁移和验证证据，但不能替代这些原始记录。尤其要记录负向变化、已知限制和结果是否回溯重算，不能只列新增功能。

## 依赖 {#dependencies}

依赖不只包括代码里直接导入的包。一次研究至少有：

- 直接依赖：研究代码明确调用的库；
- 传递依赖：直接依赖再依赖的包；
- 构建依赖：把源码分发包编译成可安装制品所需的工具；
- 运行依赖：执行时需要的解释器和包；
- 系统依赖：操作系统库、C/C++ 运行库、BLAS、时区数据库、驱动；
- 外部服务：数据接口、对象存储、数据库及其契约版本。

声明 `pandas>=2` 只给解析器一个允许集合；不同日期、索引或平台可能解析出不同闭包。精确版本也不等于精确制品：同一版本可能有多个平台 wheel，源码包还需在本机重新构建。依赖来源、文件摘要、Python 版本、平台标记和包索引同样影响结果。

SemVer 只有在上游确实遵守并准确界定公共 API 时才有信息量；小版本仍可能修复数值错误并改变结果，大版本也不表示不安全。兼容、正确和供应链可信是三个问题，应分别用契约测试、结果对照、漏洞/来源审查来评价。

升级研究依赖时，除了能否启动，还应比较关键中间量、缺失值处理、排序稳定性、随机数算法和序列化格式。仅因测试绿色便自动接受所有数值变化，或因结果变化便永远拒绝缺陷修复，都不严谨。

## 锁定文件 {#lockfiles}

依赖声明描述允许范围，锁定文件记录解析后的具体依赖闭包和制品选择。Python 的标准 `pylock.toml` 规范源自已定稿的 PEP 751，可记录适用环境、Python 要求、包、wheel/源码包、URL、索引和哈希等；具体项目也可能使用工具自有锁格式。

一个可审计锁记录至少应回答：

| 问题 | 所需记录 |
| --- | --- |
| 锁了什么环境 | Python 版本范围、平台/架构、环境标记 |
| 从哪里取得 | 索引、VCS 提交、归档 URL 或本地来源 |
| 取得哪份文件 | 文件名、大小及加密摘要 |
| 谁如何解析 | 锁定工具及版本、输入声明摘要、选定 extras/groups |
| 是否完整 | 直接、传递、构建依赖和所有目标平台是否覆盖 |

锁定文件不是跨平台魔法。同一个文件可以按规范包含互斥环境标记和多平台制品，但只有列全目标环境且安装工具正确解释时才有效；否则应为不同平台维护明确命名的锁。源码分发包即使本体哈希固定，其构建工具、系统头文件和编译器未锁仍可能产生不同结果。

哈希验证的是下载字节是否与记录相同，不证明发布者身份、无漏洞或业务正确。锁定本地目录、可变分支、未固定的直接 URL 或 editable 安装会留下缺口。锁也会陈旧，应通过受审查的更新流程处理安全修复，而不是长期冻结。

## 虚拟环境 {#virtual-environments}

Python `venv` 在一个目录中提供特定解释器入口和独立的 `site-packages`，默认不读取基础环境的第三方包。它适合避免项目之间的 Python 包相互污染，但其隔离边界有限：

- 仍建立在某个基础 Python 安装之上；
- 仍共享操作系统内核、系统库、驱动、硬件和环境变量；
- 不隔离网络、进程、文件权限或秘密；
- 若启用系统包访问，Python 包隔离也会减弱；
- 虚拟环境路径可能写入脚本，官方建议将其视为可丢弃、不可搬移并按清单重建。

激活虚拟环境主要是改变命令查找路径，不会把进程放进安全沙箱。容器能再固定一层用户空间和文件系统，但通常仍共享宿主内核与硬件；可变镜像标签也不能固定内容，应记录不可变镜像摘要。

统一项目应保存创建配方和锁定文件，而不是把 `.venv` 目录提交进仓库。重建后还要核对解释器、已安装制品和系统库，不能以目录名相同推断环境相同。

## 配置隔离 {#configuration-isolation}

配置隔离的目标是让同一代码快照能在不同环境运行，同时每次运行都知道最终采用了什么。可以采用明确的覆盖层级：

```text
代码内安全默认值
  < 版本化研究配置
  < 环境/部署配置
  < 本次运行显式覆盖
```

“后者覆盖前者”只是示例，项目必须冻结实际优先级，并在启动时验证未知键、类型、范围和互斥条件。最终生效配置要规范化后求摘要；仅记录某个输入文件不够，因为环境变量和默认值也可能改变结果。

研究相关配置包括时区、交易日历、复权口径、缺失值政策、数值精度、线程数和数据端点。秘密只保存授权引用或秘密版本 ID，不把密码、令牌和连接串写入版本库、运行清单、异常或制品。环境变量是传递渠道，不自动具备加密、轮换和访问审计。

开发、测试和生产配置应有独立权限和资源命名空间，避免研究运行误写生产结果。配置隔离也不等于结果可比：若数据端点虽名称相同却返回可变数据，仍需独立的数据快照证据。

## 随机种子 {#random-seeds}

伪随机数生成器从内部状态确定地产生序列；同一种子只有在足够多的条件相同时才帮助复现。统一研究若用随机抽样，应记录：

```text
library: numpy
version: 2.5.x
bit_generator: PCG64DXSM
root_seed: 20260814
stream_scheme: SeedSequence.spawn
worker_mapping: stable_worker_id_v1
```

仅写 `seed=42` 不足。生成器算法、库版本、调用顺序、样本排序、并行任务到随机流的映射、线程调度和硬件算法都可能改变结果。全局随机状态还会让一个新函数多抽一次数，导致下游全部漂移；更稳妥的是把生成器显式传入，并为不同任务派生独立、可记录的子流。

即使随机流完全一致，并行浮点归约、GPU 非确定算法、外部服务和未稳定排序仍可能导致差异。种子控制的是所声明的伪随机源，不是整个计算世界。若需要严格续跑，可在安全边界内记录生成器状态，但要同时记录它对应的算法和版本。

固定研究种子也不能用于密码、令牌或安全密钥；安全随机性追求不可预测，通常不应可复现。重复使用同一种子还有可能让模型选择过度适配某次划分，应结合多个预先规定的种子或独立样本评价。

## 数据快照 {#data-snapshots}

数据快照是某个可识别时点、按明确规则冻结的一组数据及元数据。仅保存查询语句 `WHERE trade_date <= '2025-12-31'` 不足，因为上游可能回填、修订、删除或改变映射。统一项目的快照清单可记录：

| 字段 | 示例 |
| --- | --- |
| 快照 ID | `cn-eod-20260813-v3` |
| 取得/可得时点 | `2026-08-14T01:20:00Z` |
| 观察期 | `2021-01-01/2025-12-31` |
| 分区清单 | 每个分区路径、行数、字节数和 SHA-256 |
| 模式 | 字段、类型、单位、主键、空值和时区 |
| 处理链 | 原始源→公司行动调整→质量规则 |
| 授权 | 许可、用途、主体、到期与再分发限制 |

“截至日”要区分观察日期、发布日期、取得日期和当时可得版本，避免回看偏差。价格、财报和成分数据还需记录修订、公司行动、退市样本及证券标识映射。快照可以是不可变表版本、内容寻址对象集合或受控归档，不一定复制成一个大文件，但引用必须在保留期内可解析。

可复现要求不凌驾于法律和合同。涉及个人信息、金融账户或其他受限数据时，应遵守合法基础、目的限制、最小必要、权限、加密、保留/删除和跨境要求；不能为了“公开复现”擅自发布原始数据。可改为发布模式、摘要、生成规则和受控访问流程；FAIR 中的 Accessible 也允许认证与授权，而非一律公开。

## 参数记录 {#parameter-recording}

参数是一次运行中由研究者或规则选择的可变输入。应记录最终值，也记录单位、类型、默认来源和选择过程。动量示例至少包括：

```yaml
lookback_sessions: 20
skip_sessions: 1
rebalance: month_end
selection_quantile: 0.20
weighting: equal
transaction_cost_bps_one_way: 8
train_period: [2021-01-01, 2024-12-31]
test_period: [2025-01-01, 2025-12-31]
```

显式传入、默认采用和由其他参数推导出来的值都要进入最终参数表。例如 `one_way_cost=8 bps` 与 `round_trip_cost=16 bps` 必须标明换算，不能只写“成本 8”。日期端点是否包含、窗口按交易日还是自然日、分位数算法和空值政策也属于参数语义。

若从 100 组组合中挑选最好结果，不能只保存胜出参数；还应保存搜索空间、生成顺序、停止规则、评价指标和全部结果，以识别多重尝试与选择偏差。参数文件应采用稳定序列化和模式版本，区分整数、浮点、字符串、`null` 与缺省；浮点值还应记录足以重建的精度。

参数记录不能包含秘密。数据访问凭据、个人身份信息和私钥应通过授权引用解析，运行清单只记录不敏感的版本或引用标识。

## 运行清单 {#run-manifest}

运行清单是把所有输入与输出连接起来的机器可读索引。一个最小示例为：

```yaml
manifest_schema: "1.0"
run_id: "mom20-20260814T021500Z-r001"
started_at_utc: "2026-08-14T02:15:00Z"
code:
  repository: "research/momentum-lab"
  commit: "6f3c...完整对象ID..."
  worktree: "clean"
dependencies:
  lock_digest: "sha256:..."
  installer_version: "..."
environment:
  python: "3.14.6"
  os_arch: "linux-x86_64"
  image_digest: "sha256:..."
data:
  snapshot_id: "cn-eod-20260813-v3"
  manifest_digest: "sha256:..."
config_digest: "sha256:..."
parameters_digest: "sha256:..."
rng:
  algorithm: "PCG64DXSM"
  root_seed: 20260814
entrypoint: "research.momentum:main"
status: "running"
```

运行开始前写入不可变身份和输入，结束时追加结束时间、状态、错误类别及输出清单；失败、取消和部分成功也应保留，而不是只追踪“最佳”运行。清单模式本身要版本化，时间统一含时区，路径尽量使用稳定 URI 或内容标识。

清单不是把整个环境倾倒成日志。它记录重建所需的声明信息和摘要，敏感内容留在访问受控的系统中。若允许事后修改，应保留修订历史、责任人和原因；更稳妥的是生成新版本并链接前一版本。

一份完整清单仍可能记录错误信息。其价值在于形成可核验链，使第二个人能逐项取证，而不是给运行盖“真实”印章。

## 制品 {#artifacts}

制品是运行产生并需要保存、比较或交付的输出，例如收益序列、指标表、模型参数、图表和报告。每个制品应记录：

- 稳定名称和类型；
- 产生它的 `run_id`；
- 内容摘要、字节数和存储位置；
- 模式/格式版本及必要的单位、时区和排序；
- 访问级别、保留期和许可；
- 上游制品或数据快照的派生关系。

加密摘要可以发现字节变化；数字签名或来源证明可把摘要与某个受信主体和过程关联。但摘要不证明输出正确，签名也不等于签名者的研究结论正确。验证签名还需检查证书/密钥信任、用途、时间和吊销状态。

位级比较要求序列化也确定：行顺序、浮点表示、压缩元数据、归档成员顺序和嵌入时间戳都可能改变字节而不改变研究语义。应分别定义“字节相同”和“数值在指定容差内一致”的验收规则，不能看到哈希不同就断言模型不同，也不能用宽松容差掩盖结构差异。

制品位置应不可变或有版本；“latest.csv”只能作方便指针，不能作证据标识。反序列化模型、pickle 或可执行制品可能执行不受信代码，消费方仍需来源验证和隔离。

## 实验追踪 {#experiment-tracking}

实验追踪系统把实验、运行、参数、指标、数据引用和制品组织起来。统一项目可以将一次研究问题设为实验，把每组预先规定的参数或种子设为运行，并用父子关系表达一次参数搜索。

追踪表至少要让以下比较成立：

| 对象 | 必须固定的比较键 |
| --- | --- |
| 指标 | 名称、公式版本、方向、单位、评价窗口 |
| 数据 | 快照、样本纳排、训练/验证/测试划分 |
| 参数 | 完整最终参数与搜索空间 |
| 代码/环境 | 提交、锁、配置和环境摘要 |
| 状态 | 成功、失败、取消、部分完成 |

指标名相同不保证口径相同；例如两个 `sharpe` 可能使用不同年化因子、无风险利率或波动率估计。自动记录功能能减少遗漏，却可能漏掉外部脚本、环境变量或手工数据处理，仍需与运行清单核对。

追踪记录应追加而非覆盖。修正错误指标时生成新运行或带版本的派生指标，并保留原记录；否则会产生事后选择。访问控制、备份、时间同步和制品存储权限同样重要。使用 MLflow 等工具是实现选择，不是依赖要求；一个简单、模式固定的表也能完成核心追踪。

追踪使比较更透明，不会自动解决过拟合、多重检验或因果识别。排名靠前的运行仍需独立样本、经济机制和稳健性检查。

## 可重建环境 {#rebuildable-environments}

可重建环境是凭保存的配方和材料重新创建声明范围内等价的执行环境。完整配方通常跨越：

```text
基础操作系统/架构
→ 系统库、编译器、BLAS、驱动与时区库
→ Python 解释器
→ 锁定的 Python 制品
→ 配置、区域设置、线程与硬件约束
→ 代码、数据、参数和运行入口
```

虚拟环境只覆盖其中一部分；容器镜像若以不可变摘要引用，可固定更多用户空间，但仍可能依赖宿主内核、CPU/GPU、驱动和外部网络。镜像标签、包索引和远端 API 都可能移动。需要长期重建时，应归档合法可保存的源码/制品、构建指令、基础镜像摘要和来源证明，并验证备份确实可读取。

几个常被混用的目标必须分开：

1. **环境可重建**：能按配方得到满足声明版本与接口的环境；
2. **计算可复现**：按 National Academies 的定义，用相同数据、计算步骤、方法、代码和分析条件得到一致计算结果；
3. **位级可复现构建**：相同源码、构建环境和指令生成逐字节相同的指定制品；
4. **科学可重复/可复制研究**：术语跨领域不统一；National Academies 将“新数据回答同一问题并得到一致结果”称为 replicability。

因此本项目必须给操作性定义：哪些输入必须相同，哪些平台差异允许，数值容差是多少，比较哪些制品。位级一致很强，却可能原样重建一个错误；末位浮点不同也可能不影响科学结论。反之，环境能启动不表示同样数据可取得，计算结果一致也不证明假设、因果或数据真实。

最终验收应由另一受控环境按清单重建，逐项比较输入摘要、运行清单、字节制品和容差指标，并记录失败环节。一次成功重建只是当时证据；长期可重建还取决于材料保留、授权、硬件可用性和规格迁移。
