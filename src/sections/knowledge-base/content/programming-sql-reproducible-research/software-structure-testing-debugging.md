一个金融数据程序即使只有几十行，也同时承担数据读取、口径校验、计算、写出和故障说明等职责。若这些职责缠在一起，“修一处、坏一片”往往比公式本身更危险。本页用同一个小程序贯穿：它读取按证券与交易日排列的收盘价，校验主键、顺序、币种和价格，计算简单收益率，再把结果原子化写入目标表。

统一示例只有一只虚构证券 `AAA`，币种均为 CNY：

| 交易日 | 收盘价 | 与上一日相比的简单收益率 |
| --- | ---: | ---: |
| 2026-08-10 | 10.00 | 无上一期，不计算 |
| 2026-08-11 | 10.50 | `10.50 / 10.00 - 1 = 5%` |
| 2026-08-12 | 10.50 | `0%` |
| 2026-08-13 | 10.71 | `10.71 / 10.50 - 1 = 2%` |

它看似简单，却足以暴露重复日期、乱序、缺失值、零价格、币种混用、部分写入和重复运行等真实问题。以下代码片段是可复算的设计示例；某条断言“应该通过”不等于它已经在某个具体环境中执行并通过。

## 模块化 {#modularity}

模块化不是把长文件任意切成多个短文件，而是把**可能因不同原因变化的决策**放在不同边界内，并隐藏不需要外泄的实现细节。对统一程序，可按责任拆为：

| 模块 | 对外承诺 | 隐藏的易变决定 |
| --- | --- | --- |
| `domain` | `PriceRow`、`ReturnRow`、领域错误和收益率规则 | 金额精度、校验不变量 |
| `ports` | `PriceSource`、`ReturnSink` 接口 | 不规定 CSV、数据库或对象存储 |
| `pipeline` | 读取→校验→计算→写出的用例顺序 | 不知道密码、SQL 方言和文件编码 |
| `adapters` | 把具体外部系统翻译成端口契约 | CSV 列名、数据库驱动、重试细节 |
| `config` | 把原始配置解析成已验证对象 | 环境变量、配置文件或秘密引用的来源 |
| `main` | 组装实现并启动一次运行 | 只做依赖装配，不承载业务计算 |

依赖方向应从易变基础设施指向稳定核心：适配器可以导入领域类型并实现核心定义的接口，领域模块不应反向导入某个数据库客户端。这样从 CSV 改为数据库，通常只替换适配器；收益率定义改变，则只影响领域规则及依赖该规则的测试。

David Parnas 的经典准则强调按“应隐藏的设计决定”分解，而不是按处理步骤机械分组。模块数量也不是越多越好：若两个文件总是一起变更、只能一起理解且没有独立契约，拆分只会制造跳转成本。实务上可检查三件事：谁拥有某个规则、调用者最少需要知道什么、替换实现时哪些模块不应变化。

## 关注点分离 {#separation-of-concerns}

“关注点”是需要独立推理、变更或审计的主题；“模块”只是承载它的一种结构。统一程序至少有六类关注点：

- 业务语义：简单收益率究竟用未复权、前复权还是总回报价格；
- 数据契约：`(symbol, trade_date)` 是否唯一，日期是否严格递增；
- 数值规则：使用 `Decimal` 还是二进制浮点、保留精度和舍入方式；
- I/O：文件编码、数据库事务、超时和连接释放；
- 运行策略：重试、幂等键、坏行隔离还是整批失败；
- 可观测性：日志字段、错误代码、指标与追踪标识。

分离不等于这些关注点永不交互，而是让交互通过显式接缝发生。例如解析器把字符串转为 `Decimal` 后，领域函数无需知道 CSV；编排器根据领域错误决定整批终止，但领域函数无需知道日志格式。相反，若 `compute_returns()` 内部读取环境变量、连接数据库、打印日志并吞掉坏行，一个测试就必须同时控制五种外部状态，任何口径变化都会牵动基础设施。

分层也不是唯一正确答案。极小的一次性脚本可以少分几层；但只要程序需要重复运行、替换数据源或被审计，至少应把“计算规则”和“外部世界”分开。判断是否分离成功，看的是变更传播和可独立验证程度，不是目录树是否漂亮。

## 纯函数 {#pure-functions}

纯函数在相同的**显式输入**下产生相同结果，且不改变调用者可观察的外部状态。收益率核心可写成：

```python
from decimal import Decimal

class InvalidPrice(ValueError):
    pass

def simple_return(previous: Decimal, current: Decimal) -> Decimal:
    if previous <= 0 or current <= 0:
        raise InvalidPrice("prices must be positive")
    return current / previous - Decimal("1")
```

于是 `simple_return(Decimal("10.50"), Decimal("10.71"))` 的结果是 `Decimal("0.02")`。函数没有读时钟、文件、数据库、全局价格表，也没有改写传入对象。对合法输入，可把规则直接写成数学契约：

\[
r_t=\frac{P_t}{P_{t-1}}-1,\qquad P_{t-1}>0,\;P_t>0.
\]

“没有赋值语句”不自动等于纯函数。读取可变全局变量、调用随机数、依赖当前时区或修改缓存，都是隐式输入或副作用。即使使用 `Decimal`，精度和舍入上下文也可能影响非终止小数的结果；若结果会舍入，应把精度规则固定在局部上下文或作为显式契约，而非偷偷依赖进程默认值。

纯函数也不是“永不报错”：对非法价格确定地抛出特定领域错误，仍可形成稳定契约。它更易用输入—输出例子、代数性质和边界条件验证。但纯函数不保证业务规则正确；如果输入本应使用复权价，写得再纯也只会稳定地产生错误答案。

## 副作用 {#side-effects}

副作用是函数除返回值外对外部可观察状态的影响，或对易变外部状态的读取。统一程序的读文件、查数据库、取当前时间、写结果、发日志、更新指标和获取秘密都属于边界行为。

可控副作用通常遵循“函数式核心、命令式外壳”：

1. 外壳通过 `PriceSource` 读取原始行；
2. 边界解析并校验为不可变领域对象；
3. 核心纯计算得到 `ReturnRow`；
4. 外壳通过 `ReturnSink` 在事务中写出；
5. 外壳记录一次运行的开始、完成或失败事件。

控制副作用不等于消灭副作用。程序必须读取和写入；关键是让它们位置明确、可替换且具有故障语义。写出接口应声明是“全有或全无”还是允许部分成功，并使用如 `(run_id, symbol, trade_date)` 的幂等键。否则网络超时后重试可能把三行收益率写成六行。

资源也属于状态。文件、连接和事务应通过上下文管理器或明确的 `try/finally` 释放；异常时同样清理。重试只用于被分类为暂时性的失败，并设置次数、退避、抖动和总截止时间。对重复主键、无效价格或认证失败盲目重试，只会放大负载并掩盖根因。

## 接口 {#interfaces}

接口不是“有同名方法”就结束；它是调用双方共同遵守的契约，包括输入类型、单位、顺序、前置条件、返回语义、异常、幂等性和版本兼容。示例端口可以表达为：

```python
from collections.abc import Iterable
from typing import Protocol

class PriceSource(Protocol):
    def read(self, *, as_of: str) -> Iterable[PriceRow]: ...

class ReturnSink(Protocol):
    def write(self, rows: tuple[ReturnRow, ...], *, run_id: str) -> None: ...
```

还必须用文字补齐类型没有表达的部分：`as_of` 是哪个时区的哪一日；输入按 `(symbol, trade_date)` 排序还是由调用者排序；迭代器能否只消费一次；价格单位和复权口径；空结果是合法还是错误；`write` 成功返回是否意味着事务已经提交；同一 `run_id` 重放是覆盖、忽略还是冲突。

Python `Protocol` 提供结构化子类型的静态表达，但类型标注通常不会自动在运行时验证数据库语义。适配器仍需契约测试。接口也不该把某一实现泄漏给核心，例如让 `PriceSource` 返回数据库游标，或让领域层捕获某驱动专属异常。

接口越大，替身和实现越难保持真实。让消费方拥有它真正需要的窄接口，并对版本变更说明兼容策略。接口能降低耦合，但不是零成本抽象；只有一个稳定、简单且不会替换的本地函数，不必为了“架构感”强行加端口。

## 配置 {#configuration}

配置是部署或运行之间会变化、但不应散落在业务代码里的参数，例如数据源地址、超时、批量大小、`as_of`、收益率口径版本和日志级别。秘密是配置中的敏感子集，例如数据库凭据和 API 令牌，二者不能按同一暴露标准处理。

推荐流程是“原始值→一次解析→一次验证→不可变配置对象→显式注入”：

```python
from dataclasses import dataclass

@dataclass(frozen=True)
class RunConfig:
    as_of: str
    batch_size: int
    timeout_seconds: float
    return_method: str
    secret_reference: str
```

启动时检查 `batch_size > 0`、超时上限、日期格式和允许的计算方法；失败应在读取数据前暴露。不要让每个模块自行读取环境变量，否则测试和复现无法知道真正输入。环境变量只是传递机制，并不天然加密或具备审计、轮换和最小权限；敏感值应由获授权的秘密管理设施按引用获取，且不得提交到源代码、测试夹具或配置样例。

复现运行应记录非敏感配置的版本或摘要、代码/数据版本和 `as_of`，而不是把连接字符串原样写入日志。默认值必须区分“安全默认”和“缺值即失败”：生产数据库、结算币种和复权方法通常不适合静默猜测。

## 日志 {#logging}

日志是带时间和上下文的运行事件记录，不是随手打印变量，也不是事实真相的自动证明。统一程序可采用结构化事件：

```json
{
  "event": "price_row_rejected",
  "run_id": "returns-20260813-v2",
  "symbol_ref": "asset-7f3a",
  "trade_date": "2026-08-12",
  "error_code": "DUPLICATE_KEY",
  "source_version": "prices-v41"
}
```

稳定字段便于查询和关联；消息文本只作人类说明。至少固定 UTC 时间戳、级别、事件名、运行/追踪 ID、组件、版本和错误代码，并明确记录发生在读取、校验、计算还是写出阶段。计数应可勾稽：读入 4 行、接受 4 行、生成 3 个收益率、提交 3 行。

日志不得包含密码、令牌、完整连接串、未经最小化的个人账户数据或原始敏感载荷。简单地把值 Base64 编码不算脱敏；哈希标识也要评估能否被枚举反推。外部文本需要限制长度并处理换行等日志注入风险。详细堆栈可进入权限更严、保存期明确的诊断通道，面向用户的错误消息则不暴露内部结构。

日志级别不是错误严重性的唯一刻度，采样也可能让“没看到日志”不等于“没有发生”。应记录时钟来源、保留和访问规则；对关键写入还需要数据库提交证据或审计记录交叉验证。

## 断点 {#breakpoints}

断点让调试器在特定代码位置暂停，从当前栈帧观察变量、逐语句执行或继续到下一断点。面对“`AAA` 的 2026-08-13 收益率错误”，可在 `simple_return` 入口设置条件断点：

```text
symbol == "AAA" and trade_date == "2026-08-13"
```

随后核对 `previous=10.50`、`current=10.71`、币种、复权口径和调用来源。相比在循环每一行暂停，条件断点缩小观察范围；异常断点则可在 `InvalidPrice` 首次抛出时停住，而不是等上层转换后才看模糊错误。

断点会改变程序时序。暂停持有锁、数据库事务或网络连接，可能制造或掩盖并发、超时和竞态问题；线上进程附加调试器还会引入可用性与数据泄露风险。因此应优先在受控、最小化且可复现的数据快照上调试，并限制敏感变量的查看和留存。

修改变量让程序“继续跑通”只能形成假设，不能证明修复。调试完成应把根因转换为稳定契约、可复现失败样本和适当层级的回归测试。

## 堆栈 {#call-stack}

调用堆栈记录当前执行路径的活动栈帧：函数、返回位置、局部变量和调用关系。统一程序的路径可能是：

```text
main
└─ run_pipeline
   └─ compute_returns
      └─ simple_return
         └─ InvalidPrice
```

Python traceback 通常从外层调用列到最内层抛出位置，最后显示最终异常类型和消息。真正要问的不是“最后一行是什么”，而是：非法值在哪里首次产生、哪一层本应拒绝、哪些帧只是转发。

适配器可把低层异常翻译成领域可理解的错误，同时保留因果链：

```python
try:
    rows = csv_source.read(as_of=config.as_of)
except UnicodeDecodeError as exc:
    raise SourceReadError("price file encoding is invalid") from exc
```

`raise ... from exc` 将原异常设为显式原因，便于区分“读源失败”和“管道失败”；在处理块内用裸 `raise` 可保留当前异常。吞掉原异常或只记录“failed”会切断证据，但把完整堆栈直接展示给终端用户又可能泄密。

异步任务、线程、回调和跨进程消息可能没有一条连续的本地堆栈，需要用任务 ID、追踪上下文和消息因果标识连接。堆栈是一次失败路径的快照，不说明该路径发生频率，也不能单独证明根因。

## 单元测试 {#unit-tests}

单元测试验证一个边界清晰的行为单元，重点是快速、确定、隔离且失败定位明确；“单元”不必等于一个方法，也不以是否使用数据库作为唯一判据。统一程序最自然的单元是收益率函数和序列校验器：

```python
from decimal import Decimal
import pytest

def test_simple_return():
    assert simple_return(Decimal("10.00"), Decimal("10.50")) == Decimal("0.05")
    assert simple_return(Decimal("10.50"), Decimal("10.50")) == Decimal("0")
    assert simple_return(Decimal("10.50"), Decimal("10.71")) == Decimal("0.02")

def test_rejects_nonpositive_previous_price():
    with pytest.raises(InvalidPrice):
        simple_return(Decimal("0"), Decimal("10.00"))
```

每个测试应能独立运行，不依赖顺序、真实时钟或前一测试留下的数据库状态。断言应对应公开契约和业务单位，而不是内部循环次数等可重构细节。用 `Decimal("10.50")` 而非从二进制 `float` 构造，可避免无关的表示误差；若产品契约允许容差，就明确绝对/相对容差和舍入点。

单元测试能快速覆盖正常、失败和不变量，但不能验证 CSV 编码、SQL 事务或生产权限。测试数量、行覆盖率和“全部绿色”都不是正确性的充分条件；错误的期望会把错误实现认证为正确。

## 集成测试 {#integration-tests}

集成测试验证两个或多个真实边界连接后是否遵守共同契约。对统一程序，至少应分别验证：

- CSV 适配器能按规定编码、列名、日期和小数格式生成 `PriceRow`；
- 数据库写出能在真实支持的数据库语义下提交、回滚并执行幂等约束；
- 管道把来源、核心和目标连接后，4 个价格恰好产生并写入 3 个收益率；
- 中途写入失败时，不会留下未声明的半批结果；
- 连接超时、权限错误和重复 `run_id` 被翻译成约定错误类型。

临时文件适合验证文件边界；真正依赖 SQL 方言、隔离级别或唯一约束时，内存字典不能替代对应数据库。反过来，每个测试都连接共享远程系统会变慢且互相污染，应使用隔离的临时资源、固定迁移版本和确定清理。

单元与集成不是竞争关系：前者精确定位规则，后者发现接口误解。集成测试也不等于端到端测试；它可能只覆盖一条适配器链，尚未验证部署、调度、身份权限和真实数据规模。

## 边界测试 {#boundary-tests}

边界测试先划分等价类，再检查分界点的“刚低于、恰好等于、刚高于”。统一程序的边界不是只有数组首尾：

| 维度 | 合法类 | 需要单列的边界或非法类 |
| --- | --- | --- |
| 价格 | 有限且大于 0 | `0`、负数、缺失、非数字、超出支持精度 |
| 序列长度 | 同一证券至少 2 行 | 0 行、1 行、跨证券边界 |
| 日期 | 唯一且严格递增 | 重复、倒序、非交易日是否允许 |
| 币种 | 序列内一致 | CNY 与 USD 混在相邻两行 |
| 主键 | 每个 `(symbol,date)` 唯一 | 完全重复与值冲突的重复 |
| 批量 | `1..max_batch` | 0、1、`max_batch`、`max_batch+1` |

“最大值”必须来自实际契约：数据库字段精度、业务风控限制和内存容量是不同边界。对一行证券，正确结果可能是空收益序列，也可能是“资料不足”错误，须由产品契约决定，测试不能替代决定。

边界用例还应覆盖时间与状态：月末、闰日、时区切换、空批提交、最后一行写入失败、重试恰好耗尽。不要用几个手选极端值声称穷尽；边界测试的价值在于系统化暴露分段规则，而不是堆叠罕见样本。

## 属性测试 {#property-based-testing}

属性测试先描述一类有效输入和应始终成立的性质，再由框架生成许多具体样本，并在失败后尽量缩小为较简单的反例。它不是“随便喂随机数看会不会崩”。

对任意同一证券、同一币种、日期严格递增且价格为正的序列，可以定义：

1. 若输入有 `n≥1` 行，输出恰有 `n-1` 行；
2. 常数价格序列的所有简单收益率均为 0；
3. 所有价格乘同一个正数 `k`，简单收益率不变；
4. 在约定精度下，`P_t = P_{t-1}(1+r_t)`；
5. 输出日期仍严格递增，且每个收益率日期对应输入的后一期。

第三条是变形关系。例如把 `10.00, 10.50, 10.50, 10.71` 同乘 100，仍得到 `5%, 0%, 2%`。生成器必须编码真实定义域；如果大量用过滤条件丢弃无效样本，既低效又可能漏掉关键结构。失败反例缩小后，要保留框架提供的复现信息，并把重要缺陷固化成容易读懂的普通回归用例。

属性成立也不是数学证明：只覆盖生成器能产生、运行预算实际探索的样本；性质本身可能写错，多个实现还可能共享同一错误。它应补充示例测试、边界测试和独立参照，而非替代它们。

## 测试替身 {#test-doubles}

测试替身是在测试中代替真实协作者的对象。经典 xUnit 术语可作如下工作定义，但不同框架会混用名称，团队应记录自己的含义：

| 类型 | 主要作用 | 统一程序例子 |
| --- | --- | --- |
| Stub | 对调用返回预设答案 | 来源固定返回 4 个 `PriceRow` |
| Fake | 有可工作的简化实现，但不适合生产 | 内存目标按主键保存收益率 |
| Spy | 记录实际收到的调用，供事后核对 | 记录 `write(rows, run_id)` 的参数与次数 |
| Mock | 预先声明期望交互，并据此判定测试 | 要求成功路径恰好提交一次、失败路径从不提交 |

测试可用 `StubPriceSource` 加 `SpyReturnSink` 验证“校验完成后才写出”。但若把 `compute_returns` 内每个内部函数都 mock 掉，测试只会证明 mock 脚本与实现细节一致，真实算法即使被绕过也可能绿色。优先替换不可控的系统边界，并让纯逻辑使用真实实现。

替身还会漂移：内存 Fake 可能允许生产数据库拒绝的重复键，Stub 可能漏掉流式迭代只能消费一次的特性。为每个生产适配器运行同一组契约测试，必要时用接口规格或 `autospec` 限制替身；但静态签名仍检查不了事务和时序。补丁应打在被测代码实际查找对象的命名空间，显式依赖注入通常比全局 patch 更清楚。

## 错误处理 {#error-handling}

错误处理的第一步是分类，因为“下一步怎么办”比异常名字更重要：

| 错误类 | 例子 | 默认策略 |
| --- | --- | --- |
| 数据契约错误 | 重复日期、价格≤0、币种混用 | 拒绝批次或按已声明政策隔离，不重试 |
| 配置/认证错误 | 缺少口径、凭据无效 | 启动即失败，修正配置或权限 |
| 暂时性来源错误 | 超时、限流、短暂断连 | 有上限地重试，遵守截止时间 |
| 写入冲突 | 同一幂等键内容不同 | 停止并人工核对，不能静默覆盖 |
| 程序不变量错误 | 合法输入却生成错序结果 | 视为缺陷，停止发布或运行 |

底层错误应在拥有语义的边界转换，并用异常链保留原因。错误消息分层：调用者得到稳定错误码和可行动说明；受控诊断记录保留堆栈与上下文；终端用户不接触凭据或内部路径。禁止用宽泛的 `except Exception: pass` 让管道带着不完整数据继续。

恢复策略须匹配副作用。写出应使用事务或临时结果加原子发布；重试必须幂等；部分成功需返回明确的成功/失败集合和可恢复位置。清理资源放在上下文管理器或 `finally`。所谓“降级”为上一版数据时，必须同时标注陈旧时间，不能把旧值伪装为本次成功。

一个错误被捕获不等于被解决。若上层既无恢复动作又无额外语义，过早捕获只会丢失堆栈。相反，将底层数据库异常一路暴露给业务调用者又造成耦合；合适的边界应保留因果、转换语义并维持可诊断性。

## 代码审查 {#code-review}

代码审查是另一位审查者基于需求、变更、上下文和证据寻找风险的过程，不是对作者或代码风格的投票。对统一程序，可沿一条真实数据路径审查：

1. 从 `PriceSource` 的输入契约追到 `PriceRow`，核对日期、币种、复权和精度；
2. 对 `10.00→10.50→10.50→10.71` 手算 `5%→0%→2%`，再追到实现和断言；
3. 注入重复日期、零价格和写入超时，检查错误分类、异常链、日志和事务；
4. 核对依赖方向，确认领域层没有读取环境、连接数据库或隐式取时钟；
5. 核对秘密、个人信息和原始载荷没有进入代码、夹具、日志或错误消息；
6. 检查单元、集成、边界和属性测试分别覆盖了什么，以及哪些风险仍未覆盖；
7. 检查重试、幂等、部分失败、回滚和重复运行是否一致；
8. 记录审查所依据的需求版本、数据契约、工具输出和仍存疑点。

审查评论应可定位、说明失败情景和影响，并区分“必须满足的正确性/安全性问题”“可选设计建议”和“需要证据的问题”。作者给出的截图、覆盖率或一次成功运行都只是证据的一部分；审查者也不能仅凭阅读证明没有竞态、依赖漏洞或环境差异。

自动检查适合发现可机械判定的问题，人类更擅长口径、边界、失败路径和可维护性；二者互补。一次批准表示在明确范围和证据下未发现阻断问题，不是无缺陷保证。真正可靠的闭环是：审查提出可证伪风险，测试或分析提供相应证据，遗留风险被显式记录，线上反馈再转化为新的契约与回归样本。
